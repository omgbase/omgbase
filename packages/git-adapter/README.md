# @omgbase/git-adapter

The **Git-backed history provider** for [omgbase](https://github.com/omgbase/omgbase) — modular-core Phase 6 (6a the engine-owned repository, writer and reader; 6b the remote half), the plan's "one alternative history strategy through the documented contract" (`spec/store` §5.12, `spec/surface` §3 "The git provider", `spec/cli` `history`, `spec/sync` §4.3/§6). A repository's history is kept by **one provider**: the engine's native recorder (the store's own history tables, captured inside every commit) or this one — a **bare Git repository at `<workspace>/.omgbase/git`** whose commits are built from the database rows by a **checkpoint worker** that consumes the change feed, and which may be bound to a **remote** the engine pushes to and fetches from. The core knows the provider only by name: `@omgbase/core` imports nothing from this package; the composition layer (the `omg` CLI / `omg mcp` host, a library embedding, the fixture runners) registers it before any store opens:

```ts
import { registerHistoryProvider } from "@omgbase/core";
import { gitHistoryProvider } from "@omgbase/git-adapter";

registerHistoryProvider("git", gitHistoryProvider());
```

Published on npm (`@omgbase/git-adapter`); the `omgbase` CLI depends on it and `packages/cli/src/seams.ts` is what registers it.

## What it does

- **`omg history enable --provider git [--branch <b>] [--cadence every|<ms>]`** initialises the bare repository, ensures `.omgbase/` is listed in the user's `.git/info/exclude` (never `.gitignore` — a tracked file is never edited), writes the manifest row `{ provider: "git", git_dir: ".omgbase/git", branch, cadence, ids_ref: "refs/omgbase/ids", remote: null }` and commits a **baseline** of the full current tree. One provider per repository: switching is `history disable` then `enable --provider <other>`.
- **The checkpoint worker** (`omg history checkpoint`; the freshness sweep runs it before every CLI verb; the MCP host's mutation hook runs it after every write — below): reads `changes_since` from the branch tip's `omgbase-seq` trailer, hashes each touched document's accepted bytes (`reconstruct` — the rows, never the vault's files) into a blob, builds the tree from the previous commit's tree plus the adds and removes (deleted documents leave the tree; a move is a remove + add, git detects the rename), writes the commit with trailers and moves the ref by compare-and-swap. **The no-op rule** (6b): a checkpoint whose tree equals its parent's — the bytes were already in the tree, a fetch brought them in — writes no commit; the `$git` cursor row alone advances. **The resume rule**: the tip's trailer is the position unless the cursor row names the same tip and stands further on.
- **Trailers** are the replay and identity record: `omgbase-seq: <epoch>:<seq>` (`<from>-<to>` folded), `omgbase-ts`, one `omgbase-commit: <c_id>` per row, `omgbase-origin`, `omgbase-actor`, `omgbase-plan` (when present), `omgbase-rescan: <epoch>:<head>` on a snapshot, `omgbase-merge: <remote tip>` on a merge commit, one `omgbase-doc: <doc_id> <path> <head>` per touched document (`-` for a deletion). The worker is idempotent across the gap between the database commit and the git commit: a crash before `update-ref` (the `git.commit` fault site) leaves dangling objects the next run re-creates byte for byte.
- **The ids ref** (6b): beside the content branch — a plain notes repository anyone can clone — the worker keeps a parallel commit chain on `refs/omgbase/ids` whose tree holds one blob per live document at `.omgbase/ids/<doc_id>`: canonical JSON `{ "blocks": [{ "hash", "id", "ordinal", "parent" }], "doc", "head" }` — the block identities in pre-order, parents, sibling ordinals and `raw_hash`. Each ids commit carries the checkpoint's `omgbase-seq` and `omgbase-content: <content commit sha>`. Push and fetch carry the ref; `git show refs/omgbase/ids:.omgbase/ids/<doc_id>` on a clone lists a document's id map. Restoration from it — an engine adopting a clone's identities — is 6c.
- **Cadence.** `every` is one commit per feed row; `{ debounce_ms }` folds the rows pending when the worker runs into one commit. The MCP host (`omg mcp`) hands its `onMutation` hook to `createCheckpointScheduler`: under `every` the worker runs synchronously after each successful write tool (the git history is complete without `omg sync`), under a debounce the hook re-arms one timer so a burst of writes folds into one commit `debounce_ms` after the last; a pending timer runs at shutdown.
- **The remote binding** (6b) — `omg history remote set --url <url> [--name origin] [--branch <b>] [--push off|on-checkpoint|periodic] [--fetch off|periodic|webhook]`: `config.remote = { name, url, branch, push, fetch }` and `git remote add` in the bare repository. Nothing is automatic until configured (both policies default `off`). `push: on-checkpoint` pushes after every checkpoint that committed (its outcome on the receipt), `periodic` on every freshness sweep (step 7 — the sweep is the timer, the adapter has none); `fetch: periodic` fetches on every sweep (step 8), `webhook` is **reserved** — an external caller (a webhook receiver, a cron) runs `omg history fetch`, the engine itself fetches nothing. `history remote status` (local refs only, no network): `{ remote, branch, local_tip, remote_tip, pushed_through, state: in-sync | ahead | behind | diverged | unknown }`; the same summary rides on `version.capabilities.history.remote`, so a client tells apart the current state, the locally checkpointed and the remotely synchronised.
- **Push** (`omg history push`): the branch and the ids ref, **never `--force`**. A rejected push (non-fast-forward) raises the `git_remote_diverged` alert (`{ remote, branch, local_tip, remote_tip }`) and fails with that code — `history fetch` merges the remote's commits and the push lands after. The ids ref's rejection alone (another engine's identity record on the remote) is reported as `ids: "rejected"`, never forced — reconciling two engines' identities is 6c.
- **Fetch** (`omg history fetch`): `git fetch` into the bare repository, then — the remote ahead of us: its tree changes are written into the vault **through the source boundary** (the files under the repository's root as external edits, ingested by the ordinary observe path so identities are matched by the reconcile and the feed records them — the provider never writes a row) and the branch fast-forwards; both sides moved: a **three-way merge at the tree level** with the common ancestor git supplies — a path one side changed is taken, both to the same blob is nothing, both to different blobs is a **conflict** — a clean merge is one merge commit on our branch (`omgbase-merge: <remote tip>`), conflicts keep **both versions**: ours at the path, the remote's beside it as `<stem>.remote-<short sha>.md`, the `git_merge_conflict` alert raised and no merge commit until `omg history remote resolve <path> --ours|--theirs` settles each (the last resolution writes the merge commit). The worker then finds the inbound rows' bytes already in the tree and commits nothing for them.
- **Divergence** — the remote **rewritten** (rebased, force-pushed: its tip no longer descends from the tip we last knew): detect, stop, alert. `git_remote_diverged` carries `old_remote_tip`, push and fetch pause, checkpointing continues locally, and the operator chooses `omg history remote reconcile --rebase` (replay our unpushed checkpoints onto the new head, trailers preserved, the ids ref rebased alongside, our old tip on `refs/omgbase/backup/<ts>`), `--merge` (one merge commit, both histories kept), `--adopt` (the remote's head becomes truth: its tree through the source boundary, our local edits kept beside as `<stem>.local-<short sha>.md`, our branch reset to it, the old tip backed up) or `--fork` (our branch pushed as `<branch>-omgbase-<ts>`, the human merges with git, then `--adopt`). Never a force-push, never an unpushed commit dropped without a backup ref, never a silent last-write-wins.
- **Reads** through the core's `HistoryReader` seam: `docs_history` (versions with `_commit` the git sha, `_hash` the blob's sha256, `_rev` the head token the trailer recorded), `docs_read { at: <sha> | <head token> }`, `docs_diff_unified`, the `revisions` query root; the current head is listed unretained until a commit names it. `version.capabilities.history` reports `provider: "git"`, `completeness: "every" | "checkpoints"` and `remote`.
- **Determinism**: every spawn runs `git` with `GIT_DIR`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_ATTR_NOSYSTEM=1`, no `HOME`, `LC_ALL=C`, `TZ=UTC`; the committer is `omgbase <omgbase@localhost>` (the author's name the write's actor), the dates the feed row's `ts` as `@<seconds> +0000`. Under the conformance seams the identity is `omgbase <omgbase@fixture>` (the fixtures' remote commits `remote <remote@fixture>`), so the shas the fixtures pin follow from the inputs alone. `OMGBASE_GIT_BIN` names the executable (default `git`).

## What it does not do

- **No block lineage.** Git keeps whole documents: `blocks_history` and `docs_diff` (block-grain) answer `capability_unavailable { history, unsupported, provider: "git", fix }` naming the tool that works (`docs_history`, `docs_diff_unified`). The native recorder's dispositions, retention ladder, archive segments and `history plan|export|attach|detach|list` do not apply — a git history is managed with git.
- **Checkpoint granularity.** Capture is asynchronous: a document changed twice before the worker runs is committed at its later bytes (the rows hold current state only); with cadence `every` and the mutation hook every write is one commit.
- **Credentials never enter omgbase.** A URL carrying a user or password is refused anywhere one is accepted (`history remote set --url`); `git` resolves access through the host (ssh keys, a credential helper, `GIT_ASKPASS`, a deploy key). For a hosted customer the account layer supplies a credential helper minting short-lived tokens — product work outside this package; the adapter is identical.
- **No restoration from the ids ref yet.** The ref is written, pushed and fetched; an engine adopting a clone's identities (and two engines reconciling their ids refs on one remote) is 6c.
- **No network of its own.** Push and fetch run when a verb, the sweep's `periodic` policies or the mutation hook run them; `fetch: webhook` names the external caller.
- **Unavailability is loud, writes continue.** When `git` is not on PATH (or the provider is not attached), every history read of a git-provider repository fails `capability_unavailable { history, unavailable, provider, reason }` and the `history_provider_unavailable` alert is raised; the engine keeps writing — the next checkpoint that runs catches up.

## Fixtures and tests

`spec/store/cases/history/git.json` pins the worker's commits as text (`git log --format=%H%n%s%n%(trailers)`, `git ls-tree -r`), the fault and its replay, the fold, purge then rescan, re-enable, the provider conflict; `spec/store/cases/history/git-remote.json` the remote half against a second bare repository under the case's temp dir (a local path, no network): the binding, push and the remote's log equal to ours, `on-checkpoint`, the rejected push, the fast-forward through the source boundary and the no-op checkpoint, the clean merge, the conflict with its sidecar, alert and resolve, the rewritten remote and each remediation, the ids ref carried; `spec/surface/cases/reads.json` `git-history` and `git-remote` the reads, `version` and the alerts; `spec/cli/cases/history.json` the verbs. `OMGBASE_CAPABILITIES=git` runs every suite with this provider and no native recorder (`pnpm conformance`). `pnpm --filter @omgbase/git-adapter test` is the unit suite: `git-adapter.test.ts` (the trailer codec, the config, the exclude file, the worker end to end) and `remote.test.ts` (the remote half end to end, the scheduler under fake timers).
