# Changelog

All notable changes to `oqx` are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow
[Semantic Versioning](https://semver.org/) (pre-1.0: a minor bump may break).

## [0.28.1] - 2026-10-26

### Patch
- `cargo publish` verifies a crate with its default features, and `oqx` has none: the five `WORDS` tables on `Consumer`, `RelOp`, `BinaryOp`, `UnaryOp` and `LogicalOp` are read only by the serde `Deserialize` impl behind the `json` feature, so the packaged 0.28.0 build printed five `dead_code` warnings that the workspace gates (`--all-features`, `-D warnings`) never saw. The constants carry `#[cfg_attr(not(feature = "json"), allow(dead_code))]`; `cargo check -p oqx --no-default-features` is warning-free. No behaviour change.

## [0.28.0] - 2026-10-26

### Minor
- OQX 0.28 — comments. `//` runs to the end of the line, `/* … */` across lines (no nesting); both are whitespace to the lexer, so they may stand wherever whitespace may (between tokens, inside a block, inside a template's `${ … }`), are not recognised inside a string literal or a template's text, and are dropped by the canonical printer (the tree records no trivia). An unterminated `/*` is the lex error `unterminated comment at <offset>`; a single `/` is still division; `#` is still a lex error. New fixture suite `spec/oqx/cases/comments.json`; both engines; `@omgbase/oqx-syntax` highlights comments in every grammar and the editor configuration gains the `comments` key (line and block toggling); the `query_syntax` manual notes the syntax.

## [0.27.0] - 2026-10-23

### Minor
- OQX 0.27 — a body's `select` names are the names of its rows everywhere. Through 0.26 only `where`, `having` and the items to an item's right saw a `select` alias; now every clause that reads the rows does — `where`, `having`, `frontier`, a `follow` destination (`follow kids` with `kids: children { where ok }`), `flatten`, a `group by` key, `order by` (`order by decade` with `decade: age / 10`) — and a nested block reads an enclosing body's alias through `^alias` (`^people count { where kind == ^k }` with `k: kind`), the alias's expression inlined shifted to the scope it is read from. An alias shadows a same-named row field wherever it is visible; `$it.name` reads the field. A block alias inlines as a value-position directive inside an expression (`where kids.size() > 1`; an error through 0.26) and still means "non-empty" alone as a leaf. In a grouped body a key that is a bare alias name takes the alias's expression and the post-group clauses read it as the key (`select kk: kind, n: count() … group by kk order by n desc`). Forward references stay errors, `^name` from a block included; `from`, `limit`/`offset` and the source are never rewritten. The tree keeps the surface form; `resolveAliases` / `resolve_aliases` perform the substitution and the `references` pass skips what they substitute. New fixture suite `spec/oqx/cases/alias-scope.json` (21 cases); the fixtures that pinned the old rule are flipped. The `query_syntax` card and manual describe the rule.

## [0.26.0] - 2026-10-22

### Minor
- **OQX 0.26 — collection-scoped queries** (`spec/oqx` 0.25 → 0.26; new suite `collection-scoped`, 28 cases: 1498 → 1526 fixtures). A query names its source as the collection before its body — `modules { select id, name where id == "launch" follow distinct ^modules { where id in ^needs depth 2 } order by $depth, name }` — instead of a `from` clause inside it. The form is the 0.17 receiver block with the implicit `collect`, so it parses to the identical tree and nothing in evaluation, planning, scoping or the AST changed; what moved is what is canonical. GRAMMAR §2 now leads with `<collection> [<consumer>] [distinct] { body }`; a body never names its source (the receiver supplied the rows), so `from E` inside a body keeps its one meaning, the re-projection (`people count { from jobs where !end }`, `follow _out_links { from _dst }`); the clause form `select … from S …` stays an accepted legacy spelling of the same tree and is no longer written anywhere. **The canonical printer** (AST.md §6) writes every query whose source can head a block collection-scoped and `collect` as the bare brace (`x collect { … }` → `x { … }`, `x collect distinct { … }` → `x distinct { … }`, the projection leading without `select`; a `collect` over a directive receiver keeps the word, `jobs first { offset 0 } collect { … }`; a literal, range, operator or aggregate source still prints in the clause form) — so `references` steps print `follow kids { … }`. The source hints were reworded (`a query must name its source before its body: \`<collection> { … }\` …`; the top-level predicate error points at `<collection> { <predicate> }`). Two more sugars desugar in the parser (suite `directive-sugar`, 28 cases): **a consumer word with no block is the directive over the empty block** — `people count`, `jobs first.employer`, `_nodes exists`, `jobs count distinct >= 1`, `follow kids first` — since a consumer word right after a complete receiver can be nothing else (the printer writes the braceless form whenever the word is written and the block is empty; the clause form's top-level `from people count` keeps its whole-query hint); and **a projection-only block over a lookup is the lookup's projection** — `jobs[0] { name }` ≡ `jobs first { name offset 0 }`, `jobs[p] { name }` ≡ `jobs first { name where p }` — refused when the outer block carries a clause of its own (it runs after the pick), when the inner directive is `distinct`, or when an outer alias would shadow a name the inner `where` reads; one consequence: `jobs[0] { name }` over no jobs is now `null` (`first` of none) where the two-directive tree gave `[]`. And **`follow` is legal in every body**: a where-position directive's block yields its walk's occurrences for the consumer to reduce (`children count { follow children } > 2`, `children { ^desc: id follow children }`; `exists`/`none` over a walk are the seeds' existence) — through 0.25 it was the eval error `` `follow` is only valid on a select-position collect ``; both engines route every consumer through one row path, so the walk, `flatten`, `group by`, ordering, `distinct` and the bound apply alike. `LANGUAGE_VERSION` 0.26 in both implementations and in `@omgbase/oqx-syntax` (assets regenerated; no lexical change — `from` stays reserved).

  - omgbase surface (patch, both engines): the `query_syntax` card and manual teach the collection-scoped form (byte-identical in TS and Rust), the tool descriptions' examples and the `omg query` help examples are respelled, the `graph` macro's `queries` text prints collection-scoped (`docs { … follow distinct _out_links { from _dst depth 2 } }`), the selector's root error reads `` `docs { … }`, `blocks { … }` or `nodes { … }` ``, the selector's expression wrapper is `docs { select __omg_x: <e> }` (a malformed slot now reports `unexpected '}'` where the leaked `from` was); `spec/surface` fixtures regenerated (`reads`, `examples`, `interop`, `tool-descriptions`), `spec/cli` `invoke` regenerated. `@omgbase/dataview` emits `<source> { select … }`. Documentation, READMEs and every example converted.

## [0.25.1] - 2026-10-20

### Patch
- **Builds on Rust 1.88+ again, and says so.** `omgbase-surface` 5.0.0 did not compile on Rust 1.92 (`error[E0658]: if let guards are experimental`, `query.rs` — the static root-name check in the surface runner used an `if let` MATCH GUARD, which only a newer rustc accepts); the arm is rewritten with the `if let` inside the arm body (equivalent: the arm fell through to `_` either way). Verified: `cargo +1.92.0 check --workspace --all-targets --all-features` compiles, `cargo fmt --check`, `cargo clippy --workspace --all-targets --all-features -D warnings` clean on 1.97, and the full `cargo test --workspace` sweep.

## [0.25.0] - 2026-10-17

### Minor
- OQX 0.25 (`spec/oqx` 0.24 → 0.25): **`flatten`** (SEMANTICS §25; new suite `flatten`, 74 cases: 1473 → 1547 fixtures). `flatten <expr> [{ … }] [as <name>]` joins the fixed clause order after `follow` and before `group by` (`select from where frontier follow flatten group by having order by limit offset`; a destination block adds `depth`) and is the ONE clause that may repeat — each fans out the rows the previous produced (a cross product per row; a later one reads the names earlier ones bound: `flatten jobs as j flatten j.tags as t`). The expression is read on each row exactly as `where` is and its value split by §3's coercion with one deliberate softening: an array → one row per element in collection order (an empty one yields NO row for that parent), an object → one row, absent → one row with the name absent (Dataview's rule: a missing field never drops the row), a scalar or a range → one row with the value (`flatten` splits a value, it sources no rows from it — never the §3 eval error; it never raises on the value). Each output row IS the parent row with the name bound at the same scope depth beside the lifts (step 4 of §2: it shadows a same-named property — `flatten tags` rebinds `tags`, `flatten tags as t` keeps the list; `$it`, `^`, `$depth` unchanged), read by a later `flatten`, `group by` (a bound name is a key; an aggregate reads it per row, `rows` re-enters the rows themselves), `having`, the projection, `order by`, a template literal, `^name` from a nested block; `where`/`frontier` run before the fan-out and a select alias is not substituted into the expression. Identity (§16): a flattened row's `$key` is the PAIR `[parent identity, element identity]` (an element's own identity when it is a row or an entry — a literal `entries(x)` yields keyed rows here as in every row position — else its structural value), nested by a chained flatten and never §3b-flattened — what `distinct`, `is` and `follow` compare. Output order is parent order then element order; `order by`, the bounds and every consumer apply to the flattened rows; a single receiver fanned out is plural. The block has NO slot of its own: `flatten tags { where … } as t` is the receiver-block sugar of GRAMMAR §2 (the `collect` op in `expr`), so `distinct` keeps its home on the op and everything a select-position block admits is admitted (a `follow`, a `group by`, a nested `flatten`; a lift is refused by the existing rule). `name` is always filled — a plain navigation's last segment, else `as` is required (`` `flatten size(tags)` needs a name (`flatten size(tags) as <name>`) — only a plain navigation names itself by its last segment ``) — and the printer ALWAYS writes `as`. Grammar: `flatten` is a clause when a value can follow it (an aggregate call included, so `flatten collect(x)` reaches `` `collect(tags)` is an aggregate and cannot be read in `flatten` ``), `as` only after a flatten expression — both contextual words (`select flatten, as from r` works); `duplicate flatten name 't'`; after `as` a keyword (`` expected a name after `as` ``), a literal word (`` `null` is a literal and cannot name a flattened value ``) or a `$`-name (`` a flattened value cannot be bound to a `$`-name ``) is refused; `flatten` alone is the stray-word hint `` unexpected 'flatten' after `from` — `flatten` takes a value to split into rows (`flatten <expr> [{ … }] [as <name>]`) ``; the clause-order sentence names `flatten`.
  - AST (`AST.md` 0.25 row): the `Flatten { expr, name }` node (serialized `kind: "flatten"`), `Query::flatten`/`Subquery::flatten` as `Vec<Flatten>` (`[]` on every body), the node spanning `flatten` through the name (or the expression); `walk::Node::Flatten`, `Clause::Flatten` (visited after `follow` at the row depth; `transform`/`strip_spans` cover it); `print` writes `flatten <expr> as <name>` after `follow` — the round-trip law holds over every fixture; `build::flatten`; `resolve` does not rewrite a flatten expression against the select (like `order by`/`frontier`).
  - `references` (§5b): the expression is a reference in clause `flatten` with the row's steps (a flatten adds NO step — a flattened row is the row); a block receiver is a normal step one deeper; a bound name read after its clause — a later `flatten`, `group by`, `having`, the select, `order by`, `^name` from a block under them — is not a reference (`is_flatten_bound`), in its own expression and before the clause it is the row's.
  - Optimizer: a flattened block is never cardinality-answered (the consumer counts flattened rows); a `flatten` expression counts for scope reads, raise-freedom (the value is coerced without error, so the clause raises only when its expression does) and lifts. No flatten-aware rewrite was needed: `optimized ≡ naive` holds over every fixture as before.
  - Engine: `flatten_scopes`/`flatten_elements` on the top-level, walk and block paths; the exists/none/count short-circuit, the `first` cap and the single-receiver rule step aside under `flatten`. `LANGUAGE_VERSION` 0.25.

## [0.24.0] - 2026-10-15

### Minor
- OQX 0.24 (`spec/oqx` 0.23 → 0.24): **`group by` with aggregates** (SEMANTICS §24; new suite `group-by`, 94 cases: 1379 → 1473 fixtures). `group by <key>, …` and `having <pred>` join the fixed clause order after `follow` and before `order by` (`select from where frontier follow group by having order by limit offset`), and the rows a body yields become ONE row per distinct key tuple. A key is shaped like a select item (`layer`, `meta.region` → `region`, `decade: (age - age % 10) / 10` — an expression key needs its alias; duplicate names refused) and compares as an identity (§16: absent ≡ null, a host row by `DataContext::identity`, else structurally); groups come in first-appearance order of the input rows. A GROUP SCOPE sits where the rows did (same depth, same enclosing scope): its row is the key record (the first row's values), so a bare key name reads the key, `$it` is the record, `$key` its structural identity, `^` the enclosing row, and `rows` — an ordinary identifier with an intrinsic meaning there — is the group's rows, a value and a receiver (`rows collect { select title }`, `rows count { where checked }`, `having rows exists { where !active }`; `^` inside reads the keys). ## [0.23.0] - 2026-10-13

### Minor
- OQX 0.23 (`spec/oqx` 0.22 → 0.23): **the `references` static pass** (`AST.md` §5b; new suite `references`, 29 cases: 1350 → 1379 fixtures; new fixture kind `expect.references`). `references::references(&query)` lists every **name a query reads from a row** — a bare identifier, a dotted navigation headed by one (one reference, the full path: `doc.layer`, `meta.owner`), an outer reference (`^title`, `1^title`; `$it` heads dropped) — in canonical source order, each as `Reference { name, clause, scope: ReferenceScope { depth, steps }, span }` over nodes borrowed from the tree. `scope.steps` is the row chain producing the scope's rows, root first with the depth each step produces (`ReferenceStep { expr: StepExpr::Expr(&Expr) | StepExpr::Follow(&Follow), depth }`): the source, a body's `from`, a block's receiver (one deeper), a `follow` node (the walk's frontier rows, which destinations are read on); an outer reference's steps are cut at its depth; the empty list is the root scope (the source head `from people` is reported there with depth 0). Not references: `$`-names, bindings, function/method names (the receiver and arguments are), projection keys, a `select` alias where the language substitutes it (the same body's `where`; items to its right — an alias's own name inside its own item is the row field; `order by`/`frontier`/`limit`/`offset`/`from`/`follow` are never rewritten, so a name there is a reference), names a nested block lifts onto the scope, and the trailing members of a navigation headed by a value (`refs(before).title` references `before` only). The pass is host-agnostic and knows no data: a host maps each scope to a row type and judges the name (omgbase's "unknown names" hints and errors, spec/surface 4.6, are built on it). `references_in_subquery(&Subquery)` runs it over a block body. Grammar, semantics and AST shape are unchanged. `LANGUAGE_VERSION` 0.23.
  - `walk::Visitor` gains the tree's lifetime — `Visitor<'a>` with `enter(&mut self, node: Node<'a>, ctx: &VisitContext<'a>)` — so a visitor may keep the nodes it is handed (the pass does). An implementor that keeps nothing writes `impl Visitor<'_> for V` and changes nothing else; `visit` is `visit<'a, V: Visitor<'a>>(root: Node<'a>, &mut V)`. (Pre-1.0: a minor bump may break.)

## [0.21.0] - 2026-10-13

### Minor

## [0.20.0] - 2026-10-11

### Minor
- OQX 0.20 (`spec/oqx` 0.19 → 0.20; 1188 → 1258 fixtures, three new suites `tuples`, `identity`, `cardinality`):

  - **`follow` loses its options block.** A brace after *any* destination opens that destination's block (`follow children { depth 2 }`, `follow a, children { id != "root" }`, `follow entries(kids) { where … }`), with the 0.17 body rules. Two clauses belong to a destination block alone, after `where` in the fixed order: `depth <1..8>` (this destination expands a frontier row only while its `$depth < n`) and `frontier <expr>` (an occurrence reached through this destination for which it holds is a frontier; read with `^` the walk's enclosing scope; seeds are never frontiers). The former `where` option is the block's `where`; `by` is gone. When several destinations reach a row in one step the first governs the occurrence. **The body that carries the `follow` may carry `frontier <expr>` too** (Brendan, 2026-10-11): it applies to the SEEDS — a seed for which it holds (read in the seed's own scope, `^` the enclosing scope, like `where`) is `$stop == "frontier"` and is not expanded, while it stays in the result — so every block that feeds rows into the walk says which of its rows are frontiers, and the frontier relevant to the current `$it` is defined separately from each destination's. The clause order of every body is `select from where frontier follow order by limit offset` (a destination block's adds `depth` after `frontier`); a body-level `frontier` without a `follow` is the parse error `` `frontier` needs a `follow` ``, a body-level `depth` an error naming the destination block; inside a destination block `frontier` is always the destination's. AST: `follow` keeps only `destinations`/`distinct`; `subquery` gains `frontier`/`depth`, `query` gains `frontier`; `print` writes `follow x collect { where … depth 2 }` and a body's `frontier` between `where` and `follow`.
  - **Tuples.** `(e1, e2, …)` with two or more elements is a value and a receiver: the elements concatenated with one level of flattening (a collection contributes its items, a row itself; an absent element nothing, a `null` is kept; duplicates kept). `size((a, b))`, `"x" in (tags, aliases)`, `(mom, dad, siblings) { name values }`, `follow (before, after) { depth 2 }` (one destination over the union). New AST node `tuple { items }`.
  - **Identity is `$key`.** One meaning — the key a row is known by — for `follow` cycle detection, the per-step union, `follow distinct`, `distinct` over unprojected rows, `is`, and reading `$key` on any row. The default is the host's identity through a new `DataContext` seam (TS: optional `identityOf(row)`, replacing the required `identity`, which stays as a deprecated alias for one minor; Rust: `identity` now has a structural default), else the row's structural value; an entry's identity is its key. The language never names an `id` property: the "`id` if present" rule is removed, and the in-memory `DefaultContext` names no identity. A block may project `$key: <expr>` to give the rows it yields that identity (`select name, $key: email from people follow next { $key: email }`); in a destination block `$key:` is not a column. Caveat: identities compare as values across the whole walk, so destinations that can reach the same rows should project the same `$key`.
  - **Result shape by receiver cardinality.** In row position an array is a collection and a non-array object is one row: a `collect` over it — `doc { title }`, `title from doc`, a nested `d: dst { title }` — yields the one record (or absent when filtered out; `doc { status == "active" }` is a conditional reach-through), not a one-element list; `values` the one value; `first`/`single` that object. A scalar in row position is an eval error (`` `s` is a string ("abc"), not a collection or an object ``) instead of a one-row collection — `list(s)` says it explicitly. A `from` re-projection or a `follow` makes the result plural. Hosts say which of their objects are collections through the new optional `DataContext.isSingle` (TS; default: a non-iterable object is one row) / `is_single` (Rust; default `true`). TS `OqxResult` for `collect` gains `single: boolean` (`unwrap` yields the record or `null`); Rust gains `OqxResult::Record(Option<Value>)`.
  - **Sugar closures.** `x { … }` ≡ `x collect { … }` wherever a value is accepted, function arguments included (`size(children { is checked })`); `x distinct { … }` ≡ `x collect distinct { … }`.

  omgbase binding (surface stays 3.0; the dialect follows the language):

  - `DataContext.identityOf` (TS) / `identity` (Rust) answers a store row's id for every kind (`doc_id`, `block_id`, `node_id`, `edge_id`), so `$key` on any hit is its id and walks dedup by it as before; the binding no longer relies on the removed `id`-property rule.

## [0.14.1] - 2026-10-09

### Patch
- Relational patterns in nested blocks stop being quadratic. The in-memory engine
  now runs every nested block through an optimizer (`optimize/`: a logical
  `BlockPlan` per block, a `Rule` interface, a fixpoint driver) with four rules,
  each proven unobservable — same rows, lifts and errors as the scan:

  - **Correlated equality → hash probe.** `^customers first { where id ==
    ^customer_id }`, `^orders collect { … where customer_id == ^id }`,
    `^customers exists { where id == ^customer_id }`, `${customers} first { … }`:
    a top-level `&&` conjunct `local == outer` (either side) is answered from a
    hash index on the receiver built once per run (per collection and path),
    with the residual conjuncts evaluated over the bucket in receiver order.
    Multiple equalities intersect smallest-first. The index reproduces §5
    equality exactly (absent ≡ null, `-0` ≡ `0`, `NaN` matches nothing, objects
    by reference). The sound rule: every conjunct left of the equality must be
    raise-free (no call, no `single`, no lift, no bound, no out-of-range binding)
    and the outer side must be raise-free and read nothing from the block's row;
    otherwise the scan runs. A receiver is indexed when it is statically stable
    (reads only the root/bindings) or when the same collection object is probed
    twice; a receiver that yields a fresh value per enclosing row is scanned.
    5k × 5k zip: ~9 ms (the scan: seconds).
  - **Invariant block hoisting.** A block that reads nothing from any enclosing
    row and lifts nothing is evaluated once per run and its value reused.
  - **Semi/anti-join short-circuit** is kept over the probe's bucket (`exists`
    stops at the first bucket row that passes).
  - **Cardinality.** `exists`/`none`/`count` with no residual predicate are
    answered from the bucket (or receiver) size without entering a row.

  `DataContext.indexFor(collection, path)` (TypeScript) / `index_for` (Rust) is
  a new optional seam for pre-built indexes; `IndexedCollection` keys under §5
  equality (it kept `null` and `undefined` apart and matched `NaN` to itself)
  and exposes `context()` (TypeScript) so a residual's nested blocks see the
  root and reuse its indexes. `InMemoryEngine` takes `{ rules, trace }`
  (TypeScript) / `with_rules` (Rust); `rules: []` is the naive scan, and the
  conformance suites prove optimized ≡ naive — result or error, stage and
  message — over every `spec/oqx` fixture. No language change.

  A `RowIndex` may also implement `lookupRows(value)` (TypeScript) /
  `lookup_rows` (Rust): the matching rows themselves, in receiver order. For a
  statically stable receiver the engine asks the context's index **before**
  reading the collection and, when it answers rows, never materializes the
  receiver (one correlation is probed — the first whose outer side is a `^`
  reference rather than a literal — and the other conjuncts, remaining equalities
  included, stay residual in their original order; a `TraceEvent` of kind
  `lookup` reports it). A statically stable receiver is now also read once per
  run when nothing is correlated, instead of once per enclosing row. Rust:
  `index_for` returns `Option<Rc<dyn RowIndex>>` and `lookup` returns
  `Vec<usize>`, so a context can create indexes on demand.

  `DataContext::materialize(value)` (Rust) / `materialize?(value)` (TypeScript)
  is a new optional seam, default identity: a context that hands out a stand-in
  for a collection it has not read yet (a lazy table handle) resolves it here.
  The engine calls it on every value it is about to observe as a value — an
  operand, an argument, a projected item, an `order by`/`distinct` key, a
  `where` scalar, a lift — and never in row position (the source, a receiver, a
  `from`, a `follow` destination), where the value reaches `to_rows`/`index_for`
  as handed out. The Rust engine's execution path was folded to mirror the
  TypeScript one: one `access` for every consumer (the `follow` seeds included),
  `scan`/`materialize`, a `memoized` helper for invariant plans, `outer_value`,
  and `lookup_order`/`residual_without` in `optimize`; optimized ≡ naive over
  every fixture, same perf.
