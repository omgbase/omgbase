# Agent guide for omgbase

omgbase ("Open Markdown Graph Base") is a versioned, addressable **graph layer over authored Markdown/YAML/JSON files**. Files stay the human source of truth for *content*; an embedded SQLite database owns *identity, history, and derived indexes*. At quiescence `sha256(file) == the current revision's rendered hash`. The engine is exposed three ways: a library (`@omgbase/core`), a CLI (`omg`), and an MCP server (`omg mcp`).

## The one rule that governs everything else

**Code and tests are ground truth.** The `docs/` folder is maintained as an as-built description of the implementation, but when a doc and the code disagree, the code wins.

If you change behavior, update the relevant doc in the same change. If you find a doc claim that no longer matches the code, fix the doc (or flag it) rather than coding to the doc.

## Reaching Brendan (`lmk`)

When you hit a stopping point — work is done, or you're blocked and need input — ping Brendan's phone: `lmk 'short message'` (a `~/bin/lmk` shim that posts to an ntfy.sh topic). Use it for genuine handoffs (a review is ready, a long build finished, you need a decision), not routine progress. Keep the message one line and specific.

## Orientation

- **Monorepo** (pnpm workspace, Node ≥ 22, pnpm 12). Packages:
  - `packages/core` — the engine. Everything of substance lives here (`packages/core/src/`): `format/` (parsers/renderers), `reconcile/`, `mutate/`, `oqx-js/` (binds `@omgbase/oqx`; `oqx/` is a thin re-export) + `search/` (lexical: FTS, RRF, `resolve`), `semantic/` (the optional semantic bundle — embeddings, vectors, the drain and its watermark/indexer — reachable only through the `SemanticProvider` seam), `graph/`, `core/store/` (SQLite schema), `core/capabilities/` (the seams), `sync/`, `mcp/`, `cli/`.
  - `packages/oqx` — `@omgbase/oqx`: the OQX query language + engine (parser, in-memory engine, `DataContext`/`QueryPlanner` seams, `node:sqlite` adapter). In-tree since ADR-019 but **standalone**: zero runtime dependencies, its own semver line, published on its own, never imports anything from omgbase. Any change here must keep it free of omgbase imports and must bump its `version` + `CHANGELOG.md`.
  - `packages/oqx-syntax` — `@omgbase/oqx-syntax`: syntax highlighting assets for OQX — the TextMate grammar (`source.oqx`), a Monaco Monarch grammar, a CodeMirror 6 stream parser (+ a CodeMirror 5 mode for Obsidian), a Prism grammar, the language configuration and metadata, adapters for Shiki / Monaco / CodeMirror / Prism / a VS Code extension (`vscode/`, with ```` ```oqx ```` Markdown fences). Everything is generated from one vocabulary + rule table (`src/vocabulary.ts`, `src/rules.ts`; `TOKEN_CLASSES` maps each token class to every target); the JSON under `syntax/` and `vscode/` is written by `pnpm build` and a test fails on drift. Lexical only, zero runtime dependencies, never imports the parser; tests run the real TextMate engine, prove TextMate parity of the Monarch, CodeMirror and Prism grammars over every `spec/oqx` fixture, and pin the vocabulary to the spec prose. Its own version line (not spec-tracked); `LANGUAGE_VERSION` must equal `spec/oqx/VERSION`.
  - `packages/cli` — the `omg` / `omgbase` binary (a thin second client over `core`; no business logic).
  - `packages/sync` — `@omgbase/sync`: the store-to-store synchronizer (ADR-014) — `Coordinator`, `EngineClient` seam (in-process or MCP), the `omgbase-sync` bin; backs `omg sync --server`.
  - `packages/embedder` — transformers.js / `Xenova/gte-base` (768-dim) embeddings, served as the `omgbase-embedder` stdio binary.

  - `packages/git-adapter` — `@omgbase/git-adapter` (private): the Git-backed history provider of modular-core Phase 6a (`spec/store` §5.12) — the checkpoint worker that builds commits in a bare repository at `.omgbase/git` from the change feed, the `GitHistoryReader`, the git plumbing wrapper; registered by the CLI/MCP host through the core's provider registry (`registerHistoryProvider`); the core imports nothing from it.
  - `packages/client` — thin remote MCP client (placeholder).

The Rust port proceeds component by component, each behind a language-neutral spec under `spec/` that both implementations run: **fixture first, TypeScript (reference) second, Rust third**. A behavior change without a fixture is not done.

The last spec of the series.
- **Data model** is three layers: **Docs → Blocks** (stable `b_` ids; the mutation anchors) **→ Nodes** (semantic projections: links, tasks, sections, anchors…).

## Build / verify

```
pnpm build        # builds packages/oqx first (core resolves its types from oqx's dist), then tsc -b across the workspace
pnpm test         # pnpm -r test (vitest; oqx uses node --test, Node ≥ 22.18); core is the big suite
pnpm lint         # pnpm -r lint
pnpm conformance  # the five-composition matrix: every fixture suite under OMGBASE_CAPABILITIES=core|history|semantic|full|git (needs pnpm build; ~35 min)
```

Always run `pnpm build && pnpm test` before considering a change done; a change to a fixture runner, a capability seam or the store's write paths also runs `pnpm conformance` (`scripts/conformance.mjs` — sequential, one ledger line per suite × composition, red on any failed cell; the Rust pairings of the interop suite are skipped without a Rust binary, `OMGBASE_RUST_BIN=/nonexistent OMGBASE_INTEROP=skip`). Two test-only environment hooks: **`OMGBASE_CAPABILITIES`** names the composition a store opens with (`spec/store` §9.6 — `full` is the default and the only one fixtures are regenerated from); **`OMGBASE_FAULT=<site>[:<nth>]`** throws an `InjectedFault` on the nth pass through one of six named sites (`recorder.capture`, `feed.append`, `commit.after-commit`, `materialize.before-write`, `materialize.after-write`, `git.commit` — `spec/store` §9.7, `packages/core/src/core/fault.ts`, pinned by `src/fault-injection.test.ts`). The migration qualification of a workspace copy is `node scripts/qualify/migrate-copy.mjs --workspace <dir> [--rust-bin …] [--before-bin …] [--with-files] [--repair] --compositions` (`docs/modular-core/migration-runbook.md`; `node --test scripts/qualify/migrate-copy.test.mjs`) — it never reads or writes the original tree (the copy's sources are re-pointed; `--with-files` copies an outside root), and `--repair` runs the `omg sync` that repairs legacy bytes (`spec/store` §5.11).

Releases run through `pnpm release` (`scripts/release.mjs`, plain Node, no dependencies; `node --test scripts/*.test.mjs` covers it). Versions are never edited by hand:

- **With every change, write a change note** `changes/<slug>.md` (format in `changes/README.md`): a flat frontmatter naming the npm packages and crates it touches with a level `major | minor | patch | none` (`none` = docs/tests, bumps nothing), then a Markdown body that becomes the changelog entry. **Run `pnpm release check` before committing** — it fails when a file under `packages/<dir>/` or `crates/<dir>/` changed (tests, corpus, README and CHANGELOG excluded) and no pending note names that package, or a note is malformed.
- **Spec tracking**: a crate or package implementing a spec (`oqx` / `@omgbase/oqx`, `omgbase-format`, `-reconcile`, `-store`, `-properties`, `-graph`, `-search`, `-mutate`, `-sync`, `-surface`; not the `omgbase` binary crate) keeps `major.minor == spec/<x>/VERSION`. `pnpm release plan` refuses a `minor`/`major` the spec did not move for, and a spec that moved without a note bumping the crate to it; `patch` never moves `major.minor`. A crate that pins a bumped dependency is patched automatically ("(pin)" in the plan).
- **The coordinator cuts the release**: `pnpm release plan` (levels folded per package, next versions, publish sequence, registry status), `pnpm release version` (bumps `package.json`/`Cargo.toml`, rewrites every inter-crate `version = "…"` pin, prepends `## [x.y.z] - date` sections to each `CHANGELOG.md` — created when missing — deletes the consumed notes, commits `release: …`; `--no-commit` leaves it staged, `--dry-run` previews, a dirty tree needs `--allow-dirty`), then `pnpm release publish` (`cargo publish -p <crate>` in dependency order, then `pnpm publish` per npm package — **npm still needs Brendan's OTP**, and since a code lives ~30 s while the registry wait between packages can run minutes, the tool asks the terminal for a fresh code right before each npm publish and again when npm rejects one as expired; `--otp <code>` covers the first npm package only; `--npm-only` / `--crates-only` / `--dry-run`; `pnpm publish:npm` is `release publish --npm-only`). Publishing compares versions against the registries (crates.io API, `npm view`), not contents.

`pnpm --filter omgbase test` includes the **CLI spec runner** (`spec/cli`, 470 cases spawning the built `omg`; ~3 min). `pnpm test` includes the **cross-engine interop suite** (`spec/surface` §7, `packages/core/corpus/surface/interop.test.ts`): it spawns both `omg mcp` and the Rust `omgbase mcp` as MCP stdio servers over one workspace, so it needs `cargo build -p omgbase` first (a missing binary fails the cross pairs; `OMGBASE_INTEROP=skip` skips them on a host without cargo — CI does this). Symmetrically, `cargo test` runs `crates/omgbase/tests/interop.rs`, which needs `pnpm build` first. `pnpm interop` at the root builds both and runs both harnesses.

Rust (when touching `crates/` or `spec/`):

```
cargo fmt --all --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features
```

## Where the authoritative truth lives for each surface

Prefer these over prose docs — they cannot drift because they *are* the implementation:

- **MCP tool surface** (names, params, behavior): the registrations and inline tool descriptions in `packages/core/src/mcp/server.ts`. This is the definitive list of tools, not `docs/mcp-api.md`.
- **Query language (OQX)**: OQX is the **`@omgbase/oqx`** package (parser + engine + semantics; in-tree at `packages/oqx` since ADR-019, still a standalone zero-dependency library published on its own version line — omgbase code must never be imported from it); omgbase binds it to the store via `packages/core/src/oqx-js/` (a `DataContext` in `context.ts` + the `oqxRun` wrapper in `run.ts`; `packages/core/src/oqx/run.ts` is a thin re-export kept for import stability). The former in-tree compiler was removed (ADR-013). Authoritative surface: the `query` tool description in `packages/core/src/mcp/server.ts`, the runnable examples in `packages/core/corpus/oqx/README.md`, and the behavioral gate `corpus/oqx/alchemy.test.ts` (+ `corpus/oqx/conformance.test.ts`, which proves the tier-3 pushdown planner equals pure in-memory). OQX is the single query + traversal surface (`<collection> { select … where … collect/exists/count … follow … order by }` since OQX 0.26; the clause form `select … from …` is still read). **Scalar semantics follow `@omgbase/oqx`, not the old CEL layer** — `docs/query-language.md` is rewritten to as-built (ADR-013 behavior changes: `!=`/negation over absent matches, case-sensitive string ops + `.lower()`/regex `matches()`, absent sorts last, arithmetic supported, `select/collect/count distinct`). The legacy CEL compiler (`search/cel/compile.ts`) was deleted in the modular-core Phase 1 (D9); `FilterInvalid` lives in `core/filter-invalid.ts` (re-exported by `search/cel/parser.ts`, whose `ast`/`lexer`/`parser` are otherwise dead); the semantic vector types moved to `core/capabilities/`; in Phase 2 the semantic layer moved to `packages/core/src/semantic/` behind `SemanticProvider` (only `index.ts` and the seam may import it; no SQL outside it names `embeddings`/`doc_embeddings`), the capability state is read from the per-repository `capabilities` manifest table (`core/store/manifest.ts`, store 17.0 slice 3e-ii; since Phase 4b the semantic row is flipped by `omg embed enable|disable` and by a CHANGE of the effective `embedding.provider`, the history row by `omg history enable|disable`, and `omg history purge [--before]` removes the recorder's rows without touching coverage — `spec/store` §5.9, §5.10, §7.6; the history reads answer a token the recorder lacks by the `spec/surface` §3 decision table — `disabled | unavailable | outside_coverage | pruned` over `id_claims.minted_at` and the coverage intervals; `docs_history` always lists the head with `retained`; `sync/capability-state.ts` renders the states), `version` reports `capabilities`, the `alerts` table is the alert channel every MCP result / CLI stderr / `doctor` surfaces (`core/store/alerts.ts`), and `OMGBASE_CAPABILITIES` is the **test-only override** that names the composition a store opens with — `core` (no history module, no semantic module — a core-only build, Phase 4a), `history` (no semantic module), `semantic` (no history module), `full` (the default; Phase 5a names the plan's four): every fixture suite (store, mutate, surface, graph, sync, search, cli, interop) runs its scripts under each, asserts the invariants that composition owns, compares through a mapping keyed on the absent module or skips the cases that need it, and prints one ledger line — `pnpm conformance` is the matrix (`spec/store` §9.6, `spec/surface` §7.3, `spec/sync` §8, `spec/cli` §8); since 17.3 (Phase 5a, D2 step two) a tombstone deletes a document's `blocks` rows in both engines. It is not a production switch: whether a repository's commits are captured is its manifest row, flipped by `omg history enable|disable` (`spec/store` §5.9); the history bundle's DDL follows the manifest and the semantic bundle's follows the composition (`spec/store` §3.1). The capability seams — `HistoryRecorder`, `SemanticProvider`, `IdentityClaims` in `packages/core/src/core/capabilities/` with `defaultCapabilities` bound by the composition layer (`sync/workspace.ts`, `mcp/server.ts`) — are what the core calls for history and semantic work; `src/dependency-direction.test.ts` + the eslint rule forbid `core/**`, `mutate/**`, `sync/**`, `oqx-js/**`, `reconcile/**` from importing the concrete history/semantic modules (`core/capabilities/import-allowlist.json` is the shrinking allowlist — empty since Phase 4a moved the recorder's writers and collection into `core/store/history-writers.ts` / `history-gc.ts`) and, since Phase 4a, forbid any SQL outside the history bundle (`graph/history.ts`, `core/store/{archive,retention,delta,history-writers,history-gc}.ts`, `core/capabilities/history.ts`, the DDL, the migration) from naming a history table; see `docs/modular-core/`.
- **SQLite schema**: `packages/core/src/core/store/schema.ts` (`SCHEMA_VERSION` + migrations; `DDL`/`HISTORY_DDL`/`SEMANTIC_DDL`), which must equal `spec/store/schema.sql`, `schema-history.sql` and `schema-semantic.sql` byte for byte (a test enforces it). Definitive over `docs/data-model.md`; the observe/commit semantics over that schema are `spec/store/README.md` §5.
- **Mutation kernel** (the six ops + macros + whole-doc reconciliation): `packages/core/src/mutate/`.
