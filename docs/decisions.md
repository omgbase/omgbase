# omgbase — Decision Log (ADRs)

Format: one ADR per decision; status is `proposed` until Brendan ratifies (`accepted`), after which changes require a superseding ADR. Implementation agents MUST treat `proposed` ADRs as binding defaults and MUST NOT silently deviate.

> All 18 ADRs remain `Status: proposed` — unratified binding defaults, not `accepted`. See `AGENTS.md` for the docs trust index.

---

## ADR-001 — TypeScript + SQLite embedded engine
**Status:** proposed
**Context:** Single-writer engine beside a working tree; target scale ≤10⁶ blocks/repo; implementation by coding agents; MCP-first surface.
**Decision:** TypeScript/Node 22, better-sqlite3 (WAL), unified/remark parse layer, sqlite-vec, FTS5, MCP TypeScript SDK. One SQLite DB per workspace under `.omgbase/`. PostgreSQL is a deferred dialect (same logical schema) adopted only when a real multi-user server exists.
**Consequences:** zero-ops local-first deployment; agent-friendly ecosystem; a documented vector-scale ceiling (~10⁵–10⁶) with pgvector as the pressure valve. Rust/comrak remains a possible future core behind the same `BlockTree` interface if parse fidelity or perf demands it.

## ADR-002 — External identity; no ID write-back into Markdown
**Status:** proposed
**Context:** Embedded IDs make matching exact until copy-paste forges them, tools strip them, and every file is polluted; heuristic reconciliation is needed regardless (foreign repos).
**Decision:** IDs are minted, opaque, repo-scoped, engine-local. The engine never injects markers. Authored anchors (`^ref`) are consumed as evidence and locators, never required.
**Consequences:** files stay pristine; identity is heuristic under out-of-band edits (mitigated by ADR-003); block IDs are not portable across engines (ADR-010).

## ADR-003 — Identity carries continuity, never truth; sync records dispositions, not operations
**Status:** proposed
**Context:** If edges/search/CAS hang off heuristic identity, matcher errors corrupt data. A file diff cannot testify to operations, only to states.
**Decision:** All operational data (edges, indexes, embeddings, rendering, CAS) derives from current parsed content. Identity threads only history/lineage. API commits record operations (intent); observed commits record dispositions (kind, confidence, reason, matcher_v). Snapshot chain is the source of truth; the commit log is the change feed (no event sourcing).
**Consequences:** matcher fallibility degrades biographies, never truth; history is honest about inference; replay/audit still possible via ops on api commits.

## ADR-004 — Canonicality split
**Status:** proposed
**Decision:** Files own content bytes; the database owns identity/history/lineage; everything else is derived and rebuildable. On any content disagreement the file wins and is ingested. Convergence invariant: at quiescence `sha256(file) == current_revision.rendered_hash`.
**Consequences:** `git pull` can never corrupt the engine; the engine can never surprise the human's files except through explicit API writes; "dual-write" reduces to two ingestion paths into one commit log.

## ADR-005 — Flat containment tree; sections are derived ranges
**Status:** proposed
**Decision:** Persist the flat CommonMark structure (headings are leaves). Sections are a per-revision derived index keyed by heading block; addressed as `{heading, scope:"section"}`. Table rows are blocks; cells are not.
**Consequences:** no section identity problem; parser-aligned storage; `under()`/section ops compile to range checks.

## ADR-006 — Relational graph; no graph database; no graph query language
**Status:** proposed
**Decision:** Edges live in interval-valid relational tables; traversal = frontier expansion/recursive CTE with budgets (depth cap 8). There is no separate graph query language (no Cypher/Gremlin): the traversal surface is the OQX `follow` operator on the one `query` surface (see 05 §3, 10). Inferred edges quarantined in a separate table, opt-in at query time.
**Consequences:** one store for graph+content+FTS+vectors; no Cypher injection/unbounded-query surface. (The originally-specified `graph_subgraph` analytics export was dropped with no replacement.)
**Update (provenance — superseded pre-OQX API):** the original Decision specified structured JSON traversal specs (`graph_traverse`/`graph_path`/`graph_subgraph`) as the public API. These were removed in favor of OQX `follow` (now folded into the Decision above), and `graph_subgraph` was dropped with no replacement. The "no graph query language / bounded traversal" principle is unchanged; only the surface moved.

## ADR-007 — Splice rendering; block-level raw retention; no CST engine
**Status:** proposed
**Decision:** Blocks retain exact raw bytes; rendering splices retained bytes for untouched blocks and op-supplied text for changed ones; trivia trailing-attaches; unknown syntax is opaque and byte-preserved. No remark-stringify for existing content; no tree-sitter/rowan machinery.
**Consequences:** byte-stable round trips at save granularity; minimal-diff renders; typed edits refused on opaque blocks (raw replace allowed).

## ADR-008 — Single-writer engine; OCC; no CRDT/OT
**Status:** proposed
**Decision:** The engine serializes all commits per repo. Concurrency is optimistic: content-hash CAS on updates, existence checks, opt-in order CAS; typed conflicts carry current truth; file-level hash CAS + ingest-and-replay handles the human/agent race.
**Consequences:** radical simplicity; correct behavior for all six torture scenarios; real-time co-editing is out of scope (Git remains the human sync layer).

## ADR-009 — RRF hybrid retrieval; content-keyed block embeddings; no learned ranker
**Status:** proposed
**Decision:** Rank fusion (RRF) over FTS5 + vectors, explainable boosts (title/heading/path/layer/recency), evidence returned per hit. Embeddings at block grain with context prefix, keyed `(content_hash, ctx_hash, model)`, async worker, explicit egress config.
**Consequences:** no score-calibration coupling; cache immune to identity errors; ranking debuggable by inspection.

## ADR-010 — Multi-engine identity is a non-goal
**Status:** proposed
**Decision:** One engine per repo is the supported topology. Two engines watching Git-synced clones will mint different block IDs; this is documented, not "fixed". If cross-engine identity is ever required, solve it then (identity-exchange protocol or `.omgbase/` sidecar manifest) with real requirements in hand.
**Consequences:** no premature distributed-identity machinery; the promise "block IDs are portable" is explicitly not made.

## ADR-011 — Projected queries: deferred, stratified, virtual-first; v1 reserves the seams
**Status:** proposed
**Context:** Embedded queries in fenced blocks whose results act as materialized data (queryable by other queries, traversals, agents) — Dataview ergonomics with dbt/materialized-view semantics. High value (dynamic set membership, self-building hubs, live rollups); classic risks (cycles, geometric explosion, autonomous file writes).
**Decision:** Defer the feature past Stage 5 (the full design is preserved in git history — the former `09-projected-queries.md`): provenance class `projected` (distinct from `inferred` — deterministic given sources); deterministic derived IDs (`v_`, no minting, no matcher); non-recursive stratified composition (reads only strictly-lower strata; conservative dependency over-approximation; cycles refused with `circular_projection`; `max_stratum` default 2); mandatory limits + per-repo fact budget with explicit truncation; async stratum-ordered refresh with staleness flags; additive-only (never mutates authored facts); no LLM calls in query blocks (determinism is load-bearing); virtual-first, file materialization a later opt-in via origin `projection` commits with matcher-skipped `attrs.generated` regions and `on_human_edit: detach`. **As-built, v1 has landed only the schema-enum reservations that keep the seams open:** `commits.origin` admits `'projection'` and `edges.provenance` admits `'projected'` (`core/store/schema.ts`), and the `v` id prefix is reserved in the minter's `IdPrefix` union (`core/ids.ts`). Authored ` ```omg ` fence blocks round-trip inert and are previewable read-only via `omg run` (`cli/src/cmd/run.ts`), which evaluates the fence as an OQX source and prints results without projecting or writing anything. Everything else the design names — the `attrs.generated` matcher-skip guard, an evaluator fact-source seam, the `projections.*` config namespace, and all materialization/refresh machinery — is **not** built.
**Consequences:** files authored with query blocks are valid and round-trip from v1 day one; no v1 architecture forecloses the feature; the explosive/recursive variants are refused by construction, not by vigilance; stored-query collections (05-… §8) later unify onto the same evaluator.

## ADR-012 — CLI: embedded second client, daemonless by default
**Status:** proposed
**Context:** All engine stages are complete but the surface is library + MCP only; humans, scripts, and shell-first agents need a terminal client. The docs already reserve the `omg` binary name (`data-model.md` §6). The tempting alternative — a mandatory daemon with an IPC protocol — buys nothing at the scale envelope and adds a lifecycle and a protocol.
**Decision:** Ship an `omg` CLI as the engine's **second client**: every command opens the embedded store directly and exits; no business logic in the CLI (design: `cli.md`). Long-lived processes are explicit (`omg watch`, `omg mcp` on stdio, with `mcp` running an in-process watcher by default). The in-process writer lock generalizes to an advisory flock (`.omgbase/writer.lock`); watcher liveness is a flock probe (`.omgbase/watch.lock`). Reads are fresh by default via a stat-prefiltered sweep backed by a new derived `file_stats` table; `--stale` opts out. Output contract: stdout is data (human columns / `--json` = library shapes verbatim / `--jsonl` / `--ids`), diagnostics and loud truncation footers on stderr, typed errors with current truth. Mutation sugar expands to `apply` changesets; multi-doc rewrites (`retarget`, `import`) are plan-by-default. No new runtime dependencies (`node:util` parseArgs).
**Consequences:** zero-ops CLI consistent with the local-first stance; correct concurrency with a running watcher/MCP session via flock + hash-based echo suppression; the library grows any behavior a command needs (keeping the MCP surface honest too); a future server mode (`omg serve`) is additive and deferred to the multi-user trigger in ADR-001.

## ADR-013 — OQX is the external `@omgbase/oqx` library; adopt its semantics contract
**Status:** proposed
**Context:** OQX was implemented twice: in-tree (`packages/core/src/oqx/`, a query-string → IR → single-SQLite-statement compiler bound to the docs/blocks/nodes/edges model and the `search/cel` scalar layer) and as the standalone `@omgbase/oqx` (oqx-js) package (a 3-tier evaluator — in-memory engine → `DataContext` seam → `PlannedEngine`/`QueryPlanner` pushdown with a SQLite adapter and in-memory residual fallback — governed by its own `oqx.semantics` contract). The two have diverged in scalar semantics (CEL vs oqx-js) and architecture. Maintaining both fights the goal of one authoritative OQX. There are no active users, so a query-language behavior change is acceptable if it is not ergonomically worse.
**Decision:** omgbase depends on `@omgbase/oqx` as the single OQX implementation (parser + planner + semantics), and **adopts the oqx-js semantics contract** rather than re-implementing CEL's rules. omgbase supplies a Tier-3 **`DataContext` + SQLite adapter** that pushes its schema, structural relations (`doc.nodes`, `section.blocks` range-containment, `doc.out/in` edge graph, `repo.*`), and domain functions (`text()`/`semantic()`/`under_*`/`yaml_path`/…) down to the existing SQLite store. Behavior changes accepted vs the old CEL layer: `!=`/negation over an absent field now matches (classical negation of typed equality); string ops (`contains`/`startsWith`/`endsWith`) are case-sensitive, with `.lower()`/`.upper()` and a real regex `matches()` newly available; comparisons allow field-vs-field; `^` reads arbitrary N scopes; `order by` sorts absent last (ascending). Divergences are pushed **upstream** into oqx-js where they are the library's concern (notably the `sortScopes` `desc` null-ordering fix), keeping the two genuinely in sync rather than forked. The internal `packages/core/src/oqx/` compiler is removed once the corpus passes at parity against the new engine.
**Pushdown reservation:** the SQLite adapter's expression translator is **recursive and semantics-faithful**, not a syntactic predicate matcher — it translates method/function chains (`$path.lower().startsWith("lab/")` → `substr(lower(d.path),1,4) = ?`, **not** `LIKE`, because oqx-js string ops are case-sensitive while SQLite `LIKE` is not) as deep as it can, with a per-subexpression residual boundary for anything untranslatable. Domain functions register through the same hook. A **differential conformance suite** runs each corpus query both fully in-memory and pushed-down and asserts identical results + order; this is the guardrail that keeps SQL optimization from drifting from the semantics contract.
**Consequences:** one OQX, shared semantics with the standalone library; the query language is more capable (regex, case control, field-vs-field, multi-scope `^`) and, where it differs, more correct (case-sensitive paths, `!=`-includes-absent). Costs: `docs/query-language.md` §3.1–§3.3/§7/§8 and the `query`-tool description in `mcp/server.ts` are rewritten off the CEL basis; the OQX compiler unit tests are replaced by engine + adapter tests while the behavioral corpus (`corpus/oqx/`) is retained as the acceptance gate; omgbase now consumes a raw-`.ts`/ESM package (Node ≥22.6 type-stripping) — resolved upstream by publishing a build, or via a local transpile step. Supersedes the in-tree OQX engine; the `follow`/bounded-traversal and "no separate graph query language" principles of ADR-006 are unchanged (only the implementation moves).

## ADR-014 — Sync is a standalone MCP-client service; a repo owns identity, not a filesystem
**Status:** proposed
**Implemented (2026-09):** all six stages shipped (`docs/sync-service-design.md` §9; merged in PR #8, `bc381c9`) — `packages/sync` (`Coordinator`, `EngineClient`, `omgbase-sync`), the `observe`/`observe_many`/`observe_delete` tools, the `DocStore` seam, the wired source registry (`omg source`), and the `root_path` removal. As-built, the removal was **one** schema v13 migration that runs `ALTER TABLE repos DROP COLUMN root_path` after migrating each `root_path` into an attached `fs` source (`core/store/store.ts` `migrateV13`; SQLite ≥ 3.35 via better-sqlite3) — not the table-rebuild described below. Still deferred: durable `sync_state` cursors and the optional `subscribe`.
**Context:** "Sync" is currently three fused, in-`core` things reached in-process against the `Store`: the reconciliation driver (`sync/driver.ts`), the filesystem binding expressed as the `repos.root_path` column (read by the write path, freshness, repo selection, and the watcher — ~117 call sites), and `attach` (three overlapping impls = "create repo row + one-shot ingest a folder"). Two forces split this apart: (1) remote/headless `omg mcp` servers have no local working tree and don't need one — the DB already holds a byte-exact file representation (blocks' raw bytes + trivia + frontmatter; `docsRead`/`renderDoc` reconstruct byte-for-byte, guaranteed by ADR-004's convergence invariant); (2) the schema already reserves `adapters`/`sources`/`attachments`/`sync_state` (v9) for multi-source repos, and `root_path` is the v1 shortcut that predates wiring them. Design detail: `docs/sync-service-design.md`.
**Decision:** Reify sync as **`@omgbase/sync`**, a coordinator that treats **omgbase as one peer behind its MCP interface** and each external store as another peer behind the existing source-adapter NDJSON protocol (`sync/external-source.ts`). Reconciliation, identity threading, and the echo gate stay engine-owned (ADR-003) and are reached over MCP via `docs_update` (api-origin, write *through* the engine) and a new **`observe`** tool (observed-origin, write *around* the engine — the sync service mirroring an external edit); the service threads no block identity itself. A **`DocStore` seam** replaces `apply.ts`'s direct `node:fs` calls (`FsDocStore` = today's behavior; `NullDocStore` = headless DB-canonical repo where the file-write is a no-op and the DB *is* the artifact). A **repo owns identity + history, not a filesystem**: a filesystem folder becomes *one attached `fs` source*, `attach` becomes sugar for source-add + attach + initial sync, and `repos.root_path` is first made a derived read-through of the attached fs source and finally **removed** (table-rebuild migration, the last stage). Loop prevention moves to the coordinator, backed by `sync_state` per-path revision + coarse `origin` filtering. Additive change-feed: `changes_since` digests gain `contentHash`; an optional `subscribe` streams digests (poll via `changes_since` suffices for correctness). Staged: (1) additive MCP surface, (2) `DocStore` seam, (3) wire source tables, (4) `@omgbase/sync` package, (5) `attach`-as-sugar, (6) drop `root_path`.
**Consequences:** headless/remote and multi-source deployments become first-class; the canonicality model (ADR-004) *inverts cleanly* for a sourceless repo (no file to win → DB is the content authority, export is the sync service's job) without changing it for local repos; three duplicate `attach` paths unify; the identity/opset machinery is reused, not reimplemented, over MCP. Costs: a schema table-rebuild to drop `root_path` and a ~117-site migration to resolve the fs root from the attached source (mostly via one `repoFsRoot(repo)` helper); a new package + MCP tool surface to maintain. ADR-010 (multi-engine identity non-goal) likely stands — v1 sync is one-directional-per-path and mints no identity across engines — but peer-syncing two omgbase repos re-raises it and should be ratified if pursued.

## ADR-015 — OQX names are local; `$repo` is the only root handle
**Status:** proposed
**Context:** `@omgbase/oqx` ≤ 0.6 resolved a bare identifier against the current row and, when the row lacked it, climbed enclosing query scopes to the root. omgbase leaned on that climb for its root-scan receiver: a bare `repo` inside a nested block fell through to `root("repo")`, so `repo.docs collect { … == ^x }` worked from any depth. The climb made a query's meaning depend on runtime row shape (adding a same-named field to an inner row silently re-pointed an outer reference; a typo could capture an outer field; `null`/`false`/`0` had to be special-cased as "present"), and every `DataContext` had to reproduce the same `has` gate for pushdown and residual execution to agree. oqx 0.7.0 removed the climb: a bare name is the current row only, `^name` is exactly one scope out, and `DataContext.has` is gone. Without a change, omgbase's correlated `repo.*` subqueries returned `[]` silently.
**Decision:** Adopt oqx 0.7's local resolution and expose the repository root as the **`$repo` intrinsic, present in every scope** (the root and every row, store-backed or plain): `$repo.docs` / `$repo.nodes` / `$repo.blocks` / `$repo.edges` are the explicit root scans and `$repo.$id` is the repository id. No non-`$` magic names: bare `repo` is an ordinary frontmatter key. `$repo` on a doc row (formerly the repository id string) becomes the handle; the id moves to `$repo.$id`. The store context serves `$repo` from `get` like the `doc`/`block`/`section` self-aliases — a many-to-one relation of the data model, not scope magic. The SQL planner recognizes `$repo.<target>` as a pushable source; a bare `$repo` in a predicate is residual.
**Consequences:** every reference in a query is decidable from its text; correlation is always spelled (`^name`, `$repo.<target>`) and is depth-independent for root scans. Cost: a rename of `repo.` → `$repo.` across the MCP tool description, CLI help, tutorial examples, corpus, and docs, and the one intrinsic re-meaning (`$repo` id → `$repo.$id`).

## ADR-016 — `$value` and `values`: scalar collections are first-class; omgbase returns bare values as `values`
**Status:** proposed
**Context:** OQX projected every row as a record and had no way to name the current item itself, so a collection of scalars (a list-valued frontmatter property, an array binding) could be counted but not filtered by value or returned as itself, and a "give me the paths" query came back as `[{ path }]` records. `@omgbase/oqx` 0.8.0 adds `$value` (an engine-owned intrinsic of every scope — the scope's row, absent at the root, `^$value` the enclosing row) and `values` (a projection-mode word after exactly one item: the row's result is that value, not a `{ name: value }` record; valid at the top level and in any `collect`/`first`/`single` block; composes with `distinct`). It also tightened projection parsing: an unaliased item may be any expression, but a non-navigation (call/arithmetic) must be aliased unless followed by `values` — a clear error replaces a former silent misparse. The first three items of the collection-model backlog (`$value`, `values`, `entries()`) are one coherent change; `entries()` (object→collection with `$key`/`$value`) is the remaining step.
**Decision:** omgbase adopts both as-is from the library — `$value` needs no store-context work (the engine resolves it before `DataContext.get`; the SQL translator leaves it residual) — and gives the top-level `values` form a result shape: `OqxResult.values: unknown[]` replaces `hits` (which is empty) for the collect page and holds zero or one value for `first`/`single`; `truncated`/`cursor` apply unchanged. The runner implements this by renaming the single item to a reserved key, running the ordinary record projection with the injected id/path (so keyset paging and distinct-by-projection are untouched), and peeling the values off the final page. Nested `values` blocks pass through the engine untouched. The CLI prints one bare value per line (JSON for non-strings). `count`/`exists` in select position remain rejected — that is the aggregation item, designed with grouping, not smuggled in here.
**Consequences:** list properties are queryable element-wise (`tags exists { where $value == "x" }`, `tags collect { $value values where … }`) and compact "just the values" answers cost one call and no hydration. Cost: one more optional field on the `query` result that clients must know about (documented in the tool description, `query-language.md` §7, `mcp-api.md`). Superseded-by nothing; extends ADR-013/015.

## ADR-017 — `none` and `limit`/`offset`: two more kernel constructs adopted as-is; a query bound defines the set, the page walks it
**Status:** proposed
**Context:** `@omgbase/oqx` 0.9.0 adds `none { … }` (the zero-cardinality consumer: true iff the block yields no rows, exactly `!… exists`, and the spelling for universal quantification — `all { … }` was rejected because its block would mean something different from every other consumer's) and `limit N` / `offset N` (bound the row set after where/order/distinct and before the consumer reduces it, at the top level and inside any block; a bound is read as part of the block so `^n` is the enclosing row). omgbase already had a page `limit`/`cursor` on the `query` tool, so the two notions of "limit" had to be reconciled.
**Decision:** Adopt both from the library. `none` is one more scalar consumer on the result (`consumer: "none"`, `none: boolean`), rendered by the CLI like `count`/`exists`. A **query-level bound defines the result set; the tool's `limit`/`cursor` page within it** — never the other way round. On the collect path the runner lifts a top-level `limit`/`offset` out of the engine query and applies it after its own `distinct` dedup (the engine would bound raw rows before the runner dedups by user projection), then pages; top-level bounds are therefore integer literals. `first`/`single` keep the bound in the engine, whose offset-aware cap is exactly right. Nested bounds are pure engine behavior. The tier-3 planner does not push `LIMIT`/`OFFSET` (the residual applies them), and the library's own SQLite adapter guards its first/single `LIMIT` against a query bound for the same reason.
**Consequences:** "the top three by era", "docs where every task is done", and "at least two links" are one expression each, with no client-side trimming. Cost: one more optional result field (`none`), and a rule to remember — a query bound is semantic, a page limit is transport.

## ADR-018 — `entries()`: records become collections only explicitly; omgbase materializes `frontmatter` / `inline` handles
**Status:** proposed
**Context:** `@omgbase/oqx` 0.10.0 completes the collection-model change begun with `$value`/`values` (ADR-016): a plain object is never iterable, and `entries(x)` is the explicit bridge — a collection of `{ key, value }` entries where, inside the block, the scope's row is the property's *value* (`$value`, bare names) and `$key` is the key. `$key` is entry-scope-only (arrays gain no implicit index; `entries(arr)` yields numeric keys explicitly), and a free-function call may be a consumer receiver (`entries(attrs) exists { … }`). In omgbase the natural targets — `attrs`, a nested frontmatter map, a list property — are already plain values the builtin handles, but `frontmatter` and `inline` are lazy `PropSourceRef` handles served key-by-key from the `properties` table, so `Object.entries` on them yields nothing.
**Decision:** Adopt the library semantics unchanged and add one context extension: `callFunction("entries", <PropSourceRef>)` materializes that source's bag as entries — one per top-level key in key order (the table's deterministic order; authored position is not indexed — `ord` is position within a list key), each valued by the same scalar-vs-list rule as a bare `docProp` read, with flattened dotted keys folded back into a nested value. Nothing else changes: `entries(...)` is a free call, so the SQL translator leaves it residual; the runner passes it through.
**Consequences:** "show me this doc's frontmatter as rows", "docs whose frontmatter has a key matching …", and per-key inspection of `attrs` are one query each, and the `frontmatter.<k>` / `inline.<k>` reads and `entries(frontmatter)` agree by construction (same decoder). Cost: one more special case in the store context's `callFunction`.

## ADR-019 — oqx lives in the monorepo, boundary unchanged
**Status:** proposed
**Context:** Since ADR-013 `@omgbase/oqx` lived in its own repository (`github.com/omgbase/oqx`). Every language feature omgbase adopted (ADR-015–018 each shipped an oqx minor and a core change the same day) was a two-repo dance: publish oqx, wait for registry propagation, bump core's pin and `pnpm-lock.yaml`, add the new version to `minimumReleaseAgeExclude`, then land the binding. Coordinated review of "the language change and its binding" was impossible in one PR, and the separate repo carried its own CI, lockfile, and release plumbing for a package with no dependencies.
**Decision:** Relocate the package into this workspace as `packages/oqx` via `git subtree add` (full commit history preserved under the prefix). Everything else about the package is deliberately **unchanged**: it keeps the npm name `@omgbase/oqx` and its **own semver line** (0.10.1 → 0.10.2 for the move itself, so the registry's `repository`/`homepage`/`bugs` metadata get corrected on the next publish); it keeps **zero runtime dependencies** and **never imports omgbase code** — the coupling stays exactly the `DataContext` / `callFunction` / `callMethod` / `QueryPlanner` seams that `packages/core/src/oqx-js/` binds from the outside; language, engine, and public API are untouched. `packages/core` depends on it as `workspace:^` (pnpm rewrites to `^<version>` on publish). Root `build`/`typecheck` build oqx first (`pnpm --filter @omgbase/oqx build && tsc -b`) because core resolves its types from `packages/oqx/dist`; oqx is *not* a `tsc -b` project reference, since its emit relies on `rewriteRelativeImportExtensions` plus a `.d.ts` fixup script that `tsc -b` would not run.
**Consequences:** one `pnpm build` / `pnpm test` / `pnpm lint` covers the language and its binding; a language feature and its store binding land in one commit and one review; publishing is `pnpm -r publish` (oqx on its own version, the rest on theirs). Rules that keep the boundary honest: changes under `packages/oqx` must not import from any other workspace package and must bump oqx's `version` + `CHANGELOG.md`. The old GitHub repository becomes a pointer (archived; its tags remain the anchors for pre-0.10.2 changelog links). Extends ADR-013 — the *implementation* moves in-tree, the *architecture* does not.
