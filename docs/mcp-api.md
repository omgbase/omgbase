# omgbase — MCP / API Surface

**Status:** as-built reference — the tool roster below is verified 2026-10-11 against `packages/core/src/mcp/server.ts` (the 44 registered tools, their real params and inline descriptions; surface 3.0), with every row and argument name respelled to surface 5.0 "underscore = engine" (2026-10-20; `changes/surface-5-underscore-engine-names.md`). Tool names use snake_case (MCP-safe, mrplex heritage).
**Depends on:** all preceding docs. The design metric is **agent reasoning round trips**, not call count.
**Spec:** the language-neutral contract for this surface — the read/history operations, the tool catalog, its error envelope, repo scoping and ref resolution — is **`spec/surface/README.md`**, with executable fixtures under `spec/surface/cases/` (`reads.json` scripts call every read tool through the built server; the `query-*.json` suites pin the OQX binding over the alchemy corpus; `cursor.json` the cursor codec). The reference runner is `packages/core/corpus/surface/spec.test.ts` (`SURFACE_SPEC_UPDATE=1` regenerates). `interop.json` (spec §7) is the cross-engine gate: `packages/core/corpus/surface/interop.test.ts` spawns `omg mcp` and the Rust `omgbase mcp` as stdio servers over one workspace and compares every read tool's JSON in both directions, under two conformance-only environment seams `omg mcp` honors — `OMGBASE_SPEC_MINTER=sequential` (the fixture id minter) and `OMGBASE_SPEC_CLOCK=<RFC 3339>` (the process clock; `packages/cli/src/cmd/mcp.ts`). Where this doc and those fixtures disagree, the fixtures win. Result keys on the wire follow the row rule of `spec/surface` §1.2 (5.0): an engine-provided row attribute is its underscore-prefixed name (`_id`, `_path`, `_raw`, `_hash`, `_updated_at`, the foreign keys `_doc_id`, `_block_id`), a user-authored entry is its bare name, and a key that names a ROLE rather than a row attribute keeps the reference's spelling (`parent_id`, `rev`, `hasSource`, `currentRev`, `baseRevision`, `renderedHashMatch`, …) — the fixtures record them verbatim. Through 4.11 the engine attributes were bare (`id`, `path`, `hash`, …) and the authored keys sat behind `data.<k>`.

## 1. Cross-cutting response rules

These rules apply to every tool and are non-negotiable:

0. **Multi-repo (ADR-014).** Every repo-scoped tool accepts an optional `repo` (a slug); omitting it uses the server's bound default repo, so single-repo clients are unchanged. An unknown slug is a loud `repo_not_found`. Discover slugs with the `repos` tool; per-repo counts/convergence via `repos_status { repo }`. Mutators resolve the *target* repo's working-tree root, so a write always lands in the right tree.
1. **Explicit incompleteness.** Every list-shaped result carries `truncated: boolean` and, when true, `cursor`. An agent must never have to guess whether it saw everything.
2. **Budgets are first-class.** Hydrating tools (`docs_read_many`, `blocks_read_many`, …) accept `budget_tokens` (server estimates ~4 chars/token, truncates at block boundaries, sets `truncated`). Traversals bound the walk instead: `query`'s OQX `follow … { … depth n }` / `where $ordinal <= N` and the `graph` tool's `degrees`/`max_documents`.
3. **Conflicts carry current truth.** See `mutation-and-concurrency.md` §4.
4. **One resolution ladder** wherever a block is hydrated:
   - `skeleton` — ids + types + one-line labels (~6 tokens/block)
   - `outline` — skeleton + heading text + first ~10 words per block
   - `text` — visible text (block-level syntax stripped: no fences, pipes, `>` prefixes or list markers; inline syntax kept)
   - `raw` — exact Markdown source
   - `full` — `_raw` + `_hash` + `_text` + `_attrs` + placement (`_ordinal`, `_depth`, `parent_id`)

   As built, `full` is `_raw` + `_hash` + `_text` + `_attrs` + the placement flattened onto the row (`_ordinal`, `_depth`, `parent_id`); open edges and last-change info are NOT part of the resolution (they are `links`/`blocks_history`). The full ladder is a parameter of the block readers `blocks_read` and `blocks_read_many` (default `raw`); `docs_outline` accepts only `skeleton`|`outline`. The whole-document reads (`docs_read`, `docs_read_many`, `docs_read_at`) and the enumerators (`docs_tree`, `docs_list`) take no `resolution` — they return file bytes or path rows. `budget_tokens` is accepted by `docs_outline`, `docs_read_many`, `blocks_read_many`, `docs_tree`, and `docs_list`.
5. **One spelling for a row — the name rule (`spec/surface` §1.2, 5.0: "underscore = engine").** On every record kind — docs, blocks, nodes, links, revisions and the root row alike — a **bare** name is a user-authored entry and an **underscore-prefixed** name is engine-provided, however derived: `_id`, `_path`, `_raw`, `_hash`, `_updated_at`, `_created_at`, a document's `_title` (the computed title) / `_tags` (authored `tags` ∪ body `#hashtags`) / `_format`, a block's `_type`/`_text`/`_attrs`/`_depth`/`_ordinal`, the foreign keys (`_doc_id`, `_block_id`, `_dst_id`, `_dst_path`, `_uri`, `_field`), the handles `_data`/`_frontmatter`/`_inline` (`_data.<k>` ≡ the bare `<k>`; the handles are the one way to an authored key that itself begins with `_`) and the relations (`_blocks`, `_nodes`, `_out_links`, `_in_links`, `_revisions`, `_children`, `_section`, …). Nothing is reserved in the bare namespace: `title`, `tags`, `id`, `path`, `doc`, `format` are ordinary authored keys. `$` belongs to OQX (`$it`, `$key`, `$depth`, …); omgbase adds no `$` names. Collections stay bare (`docs { … }`, `^docs`, `docs count { … }`) — the collection heading a body names a collection, not a row property — and so do the row functions in call position (`text("x")`, `semantic(…)`, `under(…)`, `refs(x)`). The self aliases are gone: `$it` is the self (a bare `doc` on a document, `block` on a block, `section` on a node is now an authored key); the reach-throughs are `_doc`, `_block`, `_dst`. **Same value, same name:** a result key that carries what a row attribute yields is spelled as that attribute in EVERY tool — a `docs_read`'s `_id`, a `docs_list` row's `_path`, a revision's `_hash`, a `blocks_search` hit's `_id` are the names a `query` hit, the OQX language and the `_id`/`_path` arguments use, so a key read from any result pastes into the next `where` or call — and a key naming a role keeps its name (`rev`, `from`/`to`, `before`/`after`, `locator`, `cursor`, `parent_id`, `baseRevision`, `expected_content_hash`, `plan_id`, `new_ids`, `commit`). `properties.computed` is keyed `_title`/`_tags` (the store's rows keep `$title`/`$tags`, `spec/properties` §3.3); the authored groups `frontmatter`/`inline` stay bare. **Arguments have no tolerance:** an argument that addresses an engine field is spelled with the underscore — `_id`/`_path`/`_ids` — and a bare `{ id }`, `{ path }` or `{ ids }` is `filter_invalid { hint: "arguments", fix }` whose message names the `_` spelling ("`id` is not an argument — the document's id is `_id` (an engine field: the bare namespace is the user's)") and whose `data.fix` is the same call respelled; the retired `doc`/`block`/`node` arguments keep their messages, now pointing at `_id`/`_path`.

## 2. Resources

| URI | Content |
|---|---|
| `omg://<repo>/doc/<doc_id>[@<rev_id>]` | Document (current or at revision) |
| `omg://<repo>/block/<block_id>[@<rev_id>]` | Block subtree |
| `omg://<repo>/path/<filepath>` | Convenience → current document at path |

Tool arguments take bare IDs, and an id carries its kind (`d_`/`b_`/`n_`; a path is always a document), so there is no polymorphic read: a document is `docs_read { _id | _path }`, a block `blocks_read { _id }`, a node's block `nodes_block_read { _id }` (3.0; `read_ref` is gone — `omg cat`/`show` dispatch client-side on the ref's shape; `blocks_read` refuses an `n_` id, naming `nodes_block_read`). A block **ref** argument (the `blocks_*` mutators' `_id`/`to`/`blocks`/`at`) is what `resolveRef` (`core/read/refs.ts`) accepts as built: a block id (`b_…`), a node id (`n_…`, dereferenced to its block), or — where a document is admitted (`to`) — a doc id (`d_…`) or a document path in either form (`/a/b.md` or `a/b.md`). **Paths (spec/surface 2.0):** every path a tool *returns* — `_path` on hits, reads, lists, history, link health, search, the document operations, `apply`, `observe*` and `changes_since`; `_dst_path` on links — is the `/`-rooted reference form, the form a reference is written in; every path argument accepts both forms. The storage layer keeps the repo-relative form (`surface-paths.ts` re-shapes the other-spec results at the boundary). In-doc anchor **locators** (`projects/foo.md#Risks/p[2]`, `#^anchor`) are a design notion that is **not implemented** — nothing parses them, so such a ref is `doc_missing` (the `ambiguous_locator` error code is declared but never raised). Locators still appear in *output* as a human-legible companion: `blocks_resolve` pairs each hit's `_id` with a `locator`, and IDs are the address to use in follow-ups.

## 3. Tools

The 44 registered tools, grouped as the server wires them. Signatures below match the Zod input schemas in `server.ts`; `?` marks an optional field. Arguments follow `spec/surface` §4 "Arguments" (5.0): a tool's prefix names the row kind it addresses and `_id` / `_path` are that kind's attributes, spelled as the attributes are — a `docs_*` tool takes `_id?`/`_path?` (at least one; both must agree — `docs_diff`/`docs_diff_unified` included), a block tool `_id`, `blocks_read_many`/`blocks_check` `_ids`, `nodes_set` `_id` (the one tool that addresses `nodes` rows); no tool refers to a document of another kind, so no argument is a foreign key; role arguments keep their names (`docs`, `roots`, `to`, `blocks`, `at`, `rev`, `path_glob`, `docs_tree.path` — a prefix —, `docs_create.path`/`to_path` — where to create or move; no row carries the path yet —, `observe*.path` — a file event's path); the kernel-op grammar is spec/mutate's. There is no tolerance: `{ id }`, `{ path }`, `{ ids }` are `filter_invalid { hint: "arguments", fix }` naming the `_` spelling, the corrected call in `data.fix`. The repo-level operations carry no kind prefix (`query`, `query_syntax`, `graph`, `changes_since`, `apply`, `observe*`, `repos*`, `sync_status`, `version`), and one verb returns the row: `read`. There is no `doc` argument. Every call is shape-checked before its handler: an unknown name is `filter_invalid` with the nearest valid one and the tool's shape ("unknown argument `q`; did you mean `query`? (blocks_search takes limit?, q, repo?)"; "`doc` is no longer an argument — pass `_id` or `_path`"), the same text from both engines. Every list-of-strings argument (`docs`, `_ids`, `roots`, `select`, `blocks`, `unset`) also takes one bare string as a one-element list (surface 4.5) and a string that IS a JSON array of strings — `"[\"b_1\",\"b_2\"]"`, the list stringified — as that list (surface 4.11); a comma-joined string is still "must be an array of strings", with the comma-split call in `data.fix`, and a `[…` string that is not a JSON array of strings is the same error with the parsed array (`"[1, 2]"` → `[1,2]`) or, when it does not parse, the comma split in `data.fix`.

### Read

```
docs_outline { _id?, _path?, resolution?: "skeleton"|"outline", depth?, budget_tokens? }
```
Orientation call. Returns the indented compact text format (id, type, label per line; `§` marks section headings). `resolution` is only `skeleton` or `outline` (no `preview`/`section`/`annotate`). The workhorse orientation call.

```
docs_tree { path?, depth?, files?, updated?, limit?, cursor?, budget_tokens? }     // repo-shape orientation: tree -L depth -d + du (5.1: a directory rollup; files: true lists documents)
docs_list { path_glob?, limit?, cursor?, budget_tokens? }        // flat `ls`, paged
```
`docs_tree` is the **repo-level** orientation call — the answer to "what does this repo contain?" in one small page. The engine stores paths as flat strings; this is the one read that treats `/` as a separator. Since surface 5.1 the page is a **directory rollup**: every directory within `depth` segments under `path` (a directory prefix in either form; omit for the root; reported as `prefix`, rooted — `/` for the root, else `/<dir>/`; default depth 1 = the immediate subdirectories) is one `{ _path, docs, blocks }` entry (a rooted path ending in `/`; `docs`/`blocks` the totals beneath it; a nested directory listed after its parent in path order), and the documents directly in `path` are counted as `files_here`, not listed. `files: true` lists the documents within `depth` too, as `{ _id, _path, blocks }` (a directory ends in `/`, a document carries an `_id` — there is no `kind`); `updated: true` adds `_updated_at` to every entry (a directory's the latest last-commit time beneath it). `total: { docs, blocks }` and `files_here` always cover everything under `prefix` regardless of paging. Descend by re-calling with `path` set to a directory entry, or raise `depth`. (Through 5.0 every entry was `{ _id?, _path, kind, docs, blocks, _updated_at }` and the documents were always listed — 27 kB and a second page for a 348-document repository at depth 2; the rollup is under 1 kB.)

`docs_list` is the flat enumeration behind `omg ls`: `{ items: [{ _id, _path, _updated_at, blocks }], truncated, cursor }`, ordered by path (the row's own `_id`/`_path`/`_updated_at`, §1 rule 5; `{ id, path, updated_at, blocks }` through 4.11, `{ path, blocks, ts }` before 3.0). `path_glob` is a SQL `LIKE` match where `*` matches any run **including `/`** (`projects/*` is the whole subtree — there is no "immediate children only"; that is `docs_tree`'s job). Unscoped on a large repo it is hundreds of rows, so it is paged like every other list: `limit` (default 200) caps rows, `cursor` from a truncated page resumes after the last row returned, `budget_tokens` caps the page's estimated size (at least one row is always returned so a paging client makes progress), and `truncated` is honest. A malformed `cursor` is `filter_invalid`. All keyset cursors on this surface (`query`'s collect page, `docs_list`, `docs_tree`) share one kernel encoding (`core/cursor.ts`: opaque base64url of a string tuple) and one rejection path — a cursor handed to a tool that did not issue it is loud, never a silent restart.

```
docs_read { _id?, _path?, include_ids?, at? }
```
Reads a whole document in one call — `{ _id, _path, rev, properties, _raw }`: `_raw` is the complete file bytes (verbatim — the same bytes `apply` writes to disk, fences/tables/list markers preserved; the document's `_raw` of `spec/surface` §1.2), `properties` is the document's property bag grouped by source, `_id`/`_path` the document's identity (`id`/`path`/`raw` through 4.11; before 3.0 `content`/`docId`/`path`). The cold-start "read the guide before doing anything" call — mirrors mrplex `docs_get`. `include_ids:true` also returns the document's block ids in order (`ids`) plus `hashes` — a `{ block id → block hash }` map giving each block's current raw hash, exactly the `expect.content_hash` value raw `apply` ops (`update`/`split`/`merge`/`remove`) want. So one read yields both the stable ids AND the CAS tokens to mutate them, without a follow-up `blocks_read_many(resolution:"full")` hydration round trip. It also returns `parents` — `{block id → parent block id | null}` (null = top level) — because `ids` is a flat pre-order walk and otherwise a list is indistinguishable from its items; filtering `ids` to `parents[id] === null` gives the top-level blocks without an outline read. This is a server-side projection over ordered blocks, not blob storage: identity stays block-level (`docs_read` reads; `apply` writes via block ops). `blocks_read` on a doc/heading id returns only that block — use `docs_read` for the whole document.

`properties` is `{ frontmatter, inline, computed }` — the three property sources of the `properties` table (`properties-table.md`), each a `{ key → value }` record (`core/store/properties.ts` `docPropertiesGrouped`). `frontmatter` is format-dependent, produced by the ingest adapter, not universally a YAML fence: for markdown it is the parsed frontmatter block; for a YAML or JSON file it is the parsed object the file represents; a bespoke adapter (say a `.trx` terminal-scrape format, or a `.js` file exposing its top-level exports) extracts whatever its format defines. `inline` holds the dataview-style `key:: value` fields accumulated from the body; `computed` holds the engine's computed properties re-keyed as the attributes that read them — `_title` (the first H1) and `_tags` (the body `#hashtags`; the `_tags` attribute in a query is this list ∪ the authored `tags`) — the store's rows being `$title`/`$tags` (`spec/properties` §3.3); the authored groups `frontmatter`/`inline` are keyed by the authored names, bare. There is no `metadata` field — earlier drafts of this doc and of the tool description used that name for what is now `properties`.

**`at` (spec/surface 4.7).** `docs_read { _path, at: "<rev>" }` reads the document **as of that revision** — `{ _id, _path (as of the revision), rev (the given one), _raw (the reconstructed bytes, spec/store §6.2), renderedHashMatch }`. No `properties`: the property table is current-state only, and the authored bag is not yet recomputable from bytes in one call of the format layer, so the time-travel read carries nothing it would have to guess at. `include_ids` with `at` is `filter_invalid` "`include_ids` is not available with `at`" (block ids at a past revision are a later question); a `rev` that is not the document's is `target_missing`. Revision ids come from `query` over the `revisions` target (`revisions { _path == "/x.md" order by _seq }`), or from `docs_history`/`changes_since`/`docs_diff`. **Archived revisions (spec/surface 4.9, spec/store 15.0 §7.1):** `omg history export --prune` moves old revisions' bodies into archive segment files; such a revision is `_archived: true` on the `revisions` target and in `docs_history`, still reads byte for byte through its segment while the segment is attached, and otherwise fails `revision_archived` with `data: { rev, archive, path? }` — an operator runs `omg history attach <file>`. The same applies to `docs_read_at`, `docs_diff` and `docs_diff_unified`. There is no MCP tool for archiving or attaching: it is the operator's `omg history` surface.

```
docs_read_many { docs[], include_ids?, budget_tokens? }       // capped at MANY_DOCS_CAP refs
docs_read_at { _id?, _path?, rev }                           // time-travel whole-doc read
```
`docs_read_many` is the plural of `docs_read` and the hydrate half of query→hydrate: pass a list of refs (each a doc id OR path) and get `{ items, errors, truncated }` — one full read per ref, a ref resolving to no live doc landing in `errors` (not failing the batch), duplicates collapsed, excess refs past the cap dropped with `truncated`. Under `budget_tokens` the batch stops before the item that would exceed it — but the **first item always ships**, even when it alone exceeds the budget (the same at-least-one-row contract as `docs_list`/`docs_tree`; `blocks_read_many` likewise always returns its first resolved node), so a budgeted caller always makes progress and `truncated` only ever means "more remained". `include_ids:true` adds `ids` + `hashes` to each item, same as `docs_read`. `docs_read_at` is sugar for `docs_read { _id | _path, at: rev }` (spec/surface 4.7) — the same code path, the identical result `{ _id, _path (as of that revision), rev, _raw, renderedHashMatch }` (through 4.6 it also carried the CURRENT property bag flagged `propertiesAreCurrent: true`; gone, since a time-travel read must not present current values as historical).

```
blocks_read { _id, resolution?: "skeleton"|"outline"|"text"|"raw"|"full" }  // nodes_get, then blocks_get, before 3.0; `_id` is a block id (an n_ node id is block_missing naming nodes_block_read); the document is inferred
nodes_block_read { _id, resolution? }                          // 3.0: `_id` is a NODE id (n_…); the block it was projected from, exactly as blocks_read renders it
blocks_read_many { _ids[], resolution?, budget_tokens? }      // nodes_get_many, then blocks_get_many, before 3.0; ≤ 100 ids, any number of docs
```
`blocks_read` hydrates one block subtree at a resolution (the full ladder from §1); every row names itself `_id`. The `raw`/`full` resolutions include the block's `_raw` (its exact source bytes) and `_hash` (its sha256 — what `update`/`split` need in `expect.content_hash`); `full` adds `_text`, `_attrs` and the placement flattened onto the row — `_ordinal`, `_depth`, `parent_id` (`null` at the top level; a role key, kept bare). Through 4.11 the row keys were bare (`id`, `raw`, `hash`, `text`, `attrs`, `ordinal`, `depth`); before 3.0: `id`, `raw`, `content_hash`, `placement { parent, ordinal, depth }`. There is no `locator`/`include` param — the block id is the address and the owning doc is inferred. `nodes_block_read` is the hop from a node (an `md:link`, `md:task`, `md:section`, … occurrence found with `nodes { … }`) to the editable block that holds it: the same result and resolution ladder as `blocks_read`; an unknown node is `block_missing` "no node with id …", a node naming no live block (a block-less node, e.g. one derived from the frontmatter) `block_missing` "node … has no block". `blocks_read` itself takes a block id only — each tool's `_id` is its own kind's.

`blocks_read_many` hydrates up to 100 blocks in request order and returns `{ nodes, truncated, unresolved }`. Block ids are globally unique, so `_ids` may span any number of documents: each id is resolved to its owning doc server-side (grouped by doc, one forest load per doc). `doc`/`path` is an optional *scope* — when given, ids owned by other documents count as unresolved — never a requirement, and the owning doc is not inferred from `_ids[0]`. `unresolved` lists the requested ids (within the cap) that name no live block; ids dropped by the 100-id cap or the token budget are reported by `truncated`, not `unresolved`. Nothing is silently dropped.

There is no polymorphic `read_ref` (removed in 3.0): an id carries its kind, so a caller holding a ref picks `docs_read { _id | _path }`, `blocks_read { _id }` or `nodes_block_read { _id }` by its shape (`d_`/path → document, `b_` → block, `n_` → the node's block). `omg cat`/`omg show` make that choice client-side; `omg show --json` on a document still prints `{ kind: "document", ...docs_read }`, composed by the CLI.

### Search

```
query { query: "<OQX expression string>", limit?, cursor? }
query_syntax { section? }                                    // the ~3.5 kB card { syntax, sections } (5.1); { section: "follow" } one chapter; { section: "all" } the whole manual
blocks_search { q, limit? }                                    // FTS5 bm25 keyword search → { hits: [{ _id, _doc_id, _path, _type, _text, score }], truncated }
blocks_resolve { query, limit? }                             // hybrid ranker → [{ _id, locator, preview, evidence }]  (resolve before 3.0; blocks_search was text_search)
```
`query` takes a single **OQX string** (not a `{from, filter, …}` envelope) — composable structural navigation, correlated subqueries, `select` projection, and bounded recursive traversal (`follow`) in one expression (see graph-and-query.md §4 and 10-oqx). `limit`/`cursor` page the lean hits `{ _id, _path, …projections }` (surface 5.0: the envelope keys are the engine's `_id`/`_path`, so a hit's `_id` pastes into the next `where _id == "…"` unchanged; a `_path` projection collapses onto the envelope key and an alias `_id:`/`_path:` on anything else is refused; and every other tool spells a row the same way — `docs_list`, `docs_read`, `graph`, `blocks_read`, `blocks_search`, `blocks_resolve`, a revision — §1 rule 5); a `count`/`exists`/`none` consumer returns a scalar; a `select <expr> values` projection returns the bare values as `values` (paged the same way, `hits` empty); a query-level `limit N`/`offset N` bounds the result set that `limit`/`cursor` then page within. The connectives are `and` / `or` / `not` (`&&` / `||` / `!` accepted); sugar (oqx 0.17): a receiver block without a consumer is `collect` (`docs { type == "x" }`), a block may lead with a predicate, brackets `x[p]` / `x[p]!` / `x[n]`, postfix `x!` (required), `x is y` / `x is not y`. The repository is the root row (surface 2.0): `^docs` / `^nodes` / `^blocks` / `^links` from a top-level row (one caret per enclosing block, or `0^docs` from any depth), `^_id` the repository id, `^$it` the root object; a bare `docs` inside a block and `$repo` are errors naming the replacement. `refs(field)` resolves the document references a property holds (either path form or a `d_` id; dangling dropped) to live rows — a receiver, a source or a `follow` destination. Every path returned is `/`-rooted and every path accepted tolerates both forms (spec/surface §1 "Paths"). `query_syntax` (no args) returns that whole reference — call it before writing a non-trivial query. **Unknown names (spec/surface §1.5, 5.0):** a bare name no object of the kind carries is a property read that yields absent — on docs/blocks/nodes it is reported in `hints: [string…]`, the last member of the result (absent when there is nothing to say), with the rows still returned and the nearest match drawn from the authored keys AND the engine names ("no document in this repository carries a property `title`; did you mean `_title`?" — so a bare `title`/`id`/`path`/`tags`/`format` is pointed at its `_` spelling); on `links` and `revisions` (closed kinds: no authored data reaches them) it is `filter_invalid` (`links { select _path, target }`); a `_x` that is no engine name of the kind is `filter_invalid` naming the kind's engine names; the same name in a `plan`/`apply`/`execute` selector is refused. `blocks_search` is a plain-words FTS5 search box (words ANDed, `"quoted phrases"` adjacent, no DSL); a hit is the block row `{ _id, _doc_id, _path, _type, _text, score }`. `blocks_resolve` is the "give me the id of the thing I mean" hybrid ranker (FTS + semantic when a provider is configured) — `[{ _id, locator, preview, evidence }]`; it has no `scope`/`kinds` param.

### Graph

```
graph { roots[], degrees?, direction?: "in"|"out"|"both", predicate?, select?[], max_documents? }
```
Neighborhood convenience macro: the bounded graph AROUND one or more root documents in ONE call — `{ roots, degrees, direction, documents: [{ _id, _path, degree, frontier, …select }], links: [{ _id, _doc_id, _block_id, _via_id, _dst_id, _dst_path, _uri, _dst_kind, _predicate, _provenance, _anchor, _field }], frontier: [{ _id, _path, degree }], truncated, queries }`. A link row carries the `links` target's own field names (`spec/surface` §1.2 — the key and the target were `edges` before the 3.0 name pass, and before that a rename table spelled `src`/`dst`/`dst_uri`/`src_field`); a bare-name `select` (`["layer"]`, `["_title"]`) is its own output key, `_id`/`_path` collapse onto the envelope key exactly as a `query` hit's do, and any other expression is `sel_<i>` — a projection can never overwrite the envelope here. It is a WRAPPER that compiles its args into an OQX `follow distinct _out_links { from _dst }` / `follow distinct _in_links { from _doc }` query (the link rows walked to the documents at their other end) and runs the same `query` path (the returned `queries` field is the exact follow query generated). `roots` are doc refs (paths and/or ids, depth 0); `degrees` is max hop distance (root = 0, default 1, capped so `degrees+1 ≤ 8`); `direction` defaults `both`; `predicate` restricts the walk to one link predicate; `select` adds OQX doc projections; `max_documents` caps the set (default 200) with `truncated`.

Traversal proper is the OQX `follow` operator on the `query` tool, not a dedicated tool — reach for `query` directly when you need successor/frontier predicates, `by`-keyed identity, `$ordinal` budgets, cross-document correlation, or the `links { … }` scan: `query { query: 'docs { _path == "/x.md" follow _out_links { from _dst } }' }` (`_dst` is a link row's destination document, `_doc` its source document and `_block` — `block` since surface 4.11, `_block` since 5.0 — the source block it was written in, absent for a frontmatter link; there is no `out`/`in` relation). A `query` whose OQX fails to parse on a bracket list (`_id in ["a", "b"]` — OQX spells a collection as a tuple, `("a", "b")`) is `filter_invalid` with `; a list is written as a tuple: (…)` appended and the corrected call in `data.fix` (surface 4.11; the same for a `plan`/`apply`/`execute` selector). The old structured `graph_traverse`/`graph_path`/`graph_subgraph` tools were removed.

### Mutate

```
apply { effects[], reason? }                                 // the only real writer: plan + execute in one tx (ADR-021; 4.0: `ops` and `dry_run` retired — preview with plan)
plan { effects[] }                                            // the frozen plan for these effects; writes nothing, burns no ids (3.1)
execute { plan_id } | { plan } | { plan_id, effects[] }       // commit exactly that plan (preconditions re-validated in the tx) → receipt (3.1); 5.1: the id alone runs the plan this server remembers (its last 64 `plan` results), plan_unknown otherwise
blocks_insert { to, markdown, at?, expect? }       // sugar: one insert op, ref-resolved server-side; expect = { parent_children_hash? }
blocks_update { _id, markdown?, checked?, expect? }         // sugar: set markdown / set _attrs.checked, CAS planner-pinned (4.0: `attrs` bag retired)
blocks_move { blocks[], to, at?, expect? }         // sugar: one move op; expect = { parent_children_hash? }
blocks_remove { blocks[] }                         // sugar: one remove op (subtrees; container+descendants collapse)
blocks_split { _id, at: number[] }                 // sugar: one split op, CAS auto-pinned
blocks_merge { blocks[], separator? }              // sugar: one merge op (≥ 2 adjacent blocks)
blocks_check { _ids[], checked? }                  // macro: mark task blocks checked (or unchecked); tasks_complete { blocks[] } before 3.0
nodes_set { _id, prop, value }                     // macro: edit one prop of a projected node; node_set before 3.0
blocks_append { _id, text }                        // macro (3.0): append INTO a block — a heading's section, a container's children; a leaf is block_not_container
docs_append { _id?, _path?, text, section? }       // macro: append at the document end, or inside the section whose heading TEXT is `section`
links_stale { path_glob?, limit?, summary? }                 // READ-ONLY: surface dangling internal links (summary:true = counts only)
links_retarget { from_target, to_target, path_glob? }       // retarget effect: rewrite one link destination; commits like every tool (4.0: `dry_run`/`applied` gone — preview with plan { retarget }); result = receipt + hits + pairs
links_repair { repairs?[{from,to}], from_target?, to_target?, path_glob? }  // retarget effect: bulk stale-link repair; receipt + hits + pairs (4.0)

```

**Block-level sugar (`blocks_*`).** The six `blocks_*` tools are one-op wrappers over `apply` — one kernel op each, applied through the same changeset machinery (actor `agent:mcp`, `reason` = the tool name) and returning the same `apply` result `{ results, revisions: [{ _id, _path, _hash }], committed, diffs? }` — `_hash` is the document's hash after the commit (the rendered bytes' sha256), the same three keys a `changes_since` revision carries (`dry_run:true` returns the per-file diffs and writes nothing). What they add is **server-side ref resolution and CAS pinning**, which is what lets the CLI's block sugar (`insert`/`update`/`move`/`rm`/`split`/`merge`) run unchanged over `--server`: every `block`/`blocks` argument is a *ref* — a block id or a locator — resolved with `resolveRef`, and where the kernel wants an `expect.content_hash` the tool reads the block's current raw hash and pins it (a concurrent edit becomes `stale_expectation`, never a silent overwrite). They need a working tree: on a sourceless repo they fail `repo_not_found` ("repo has no filesystem source; mutation disabled").

- `blocks_insert` parses `markdown` into new block(s) under a parent. `to` is a ref: a **block** ref nests the new blocks under that block — which must be a **container** (Markdown: a list, list item, task, blockquote or table; spec/mutate §1.1 since 1.2), a leaf such as a heading or paragraph fails `type_mismatch` (`data: { op_index, block, type }`, message `<id> is a <type>, not a container; place relative to it with at.before/at.after or append to its section`) — so "into this heading's section / this container" is `blocks_append` and "right after this block" is `at: { after }`; a **document** ref (doc id or path) places them at the document's top level — so appending a new section is `{ to: "<path>", markdown: "## New\n\n…" }`, the positional generalization of `docs_append`. `at` places among the parent's children: `"end"` (default), `"start"`, or `{ before: <block ref> }` / `{ after: <block ref> }`. Optional `expect: { parent_children_hash }` is the **destination-parent CAS** (spec/mutate §1.2, since surface 1.2): the parent's *current* direct child ids (the top-level ids for a document `to`) joined by `,` and sha256-hexed — derive it from `docs_read include_ids` (`ids` filtered by `parents`); a mismatch is `stale_expectation` with `data.current.parent_children_hash`. `content_hash` has no meaning for insert/move (there is no target block) and is not part of their `expect`.
- `blocks_move` moves `blocks` (refs, a contiguous sibling run) under `to` at `at` (same forms). `to` is a block ref (a container, as for `blocks_insert` — a leaf is `type_mismatch` before anything moves), or the blocks' **own** document (id or path) to move them to its top level; moving to *another* document's root is not expressible and fails `target_missing` — anchor on a block in that document with `at.before`/`at.after` instead. The same `expect: { parent_children_hash }` guards the destination, checked once for the whole run before anything moves.
- `blocks_remove` removes `blocks` and their whole subtrees (into the resurrection pool). A set naming both a container and some of its descendants — e.g. every id of a section straight from `docs_read include_ids` — is fine: it collapses to the top-most blocks and the result's `removed` lists everything that left. To delete a whole document use `docs_delete`.
- `blocks_split` splits `block` at the character offsets in `at` (integers) into consecutive blocks; CAS pinned to the block's current bytes.
- `blocks_merge` merges `blocks` (≥ 2 adjacent refs) into the first, joined by `separator` (default a blank line).
- `blocks_update` — see its own description in `server.ts` (replace markdown and/or set attrs with CAS; flat `checked` sugar for tasks).
`docs_move` renames a document; block identity and history are preserved, and **the inbound links follow it** (spec/mutate 1.3). The edge index follows the path, not the identity: after the rename, links written against the old path would dangle (their open edges are re-pointed at `phantom:<old path>`, what re-extracting the source would produce), so — unless `retarget_inbound:false` — the move rewrites them in the same call: a destination-aware rewrite over the source blocks (anchors, link text, titles, and code spans preserved; absolute stays absolute, `./`/`../` is recomputed, bare root-relative stays bare) applied as CAS-checked `update` ops in the SAME transaction and commit as the move (one commit row, reason `move <old> -> <new>`, with one revision per rewritten source document; `spec/mutate` 2.1 — through 2.0 the rewrites were a second changeset with reason `retarget inbound links <old> -> <new>`, committed after the move with a gap). Phantom edges already written against the new path are adopted and resolve to the moved doc either way. The result is `{ _id, _path, committed, dangling, retargeted }` — `retargeted` lists the touched `blocks`/`docs` (`null` when opted out or nothing linked in); `dangling` lists each inbound occurrence still naming the old path as a link row `{ _doc_id, _path, _block_id, target, _anchor, _field? }` (the `links` target's names; `target` is a role) — with the default, only frontmatter relations (`_block_id` `null`; a move never rewrites frontmatter, use `docs_set_meta`), with `retarget_inbound:false` every authored link too, which `links_stale` then reports. Self-doc pure-fragment links `#H` are not path-dependent and are never listed. `retarget_inbound:false` is for the rarer intent that the old path become unbound (or point at a replacement document).

**Effects (ADR-021, surface 3.1 / spec/mutate 2.3 §11).** `plan { effects }` takes an ordered list of the nine public effects — `create`, `insert`, `set`, `unset`, `move`, `remove`, `split`, `merge`, `retarget` — over typed targets (`{kind:"document", _id|_path}`, `{kind:"block", _id}`, `{kind:"node", _id}`, the derived `{kind:"section", heading_id}` range; the bare forms — a path, a `b_`/`d_`/`n_` id, `$new.n` — are unchanged) with `field` spellings for `set`/`unset` (`_frontmatter.<key>`, `content`, `markdown`, `_attrs.checked`, a node's `value`/`name`/`checked` — an editor's property name, bare) and optional `expect` guards, and returns a frozen plan: `{ version, planner_v, effects (resolved), opset (the lowered kernel ops + `creates`/`moves[{ _id, from, to }]`/`tombstones[{ _id, _path }]`/`set_frontmatter[{ doc, raw }]`), preconditions (each touched doc's `{ _id, _path, base_revision, _hash }` + `blocks[{ _id, content_hash }]` + `parents[{ doc, parent, parent_children_hash }]`), new_ids ([`$new.n` symbols]), plan_id, diagnostics, preview }`. `plan_id` is sha256 over the canonical JSON of everything but `preview`, so two engines digest the same intent identically and a client may echo a plan without its preview (5.0 respelled the digested row keys, so every `plan_id` moved). Planning writes nothing and burns no ids (new identities are symbolic). `preview.diffs` — the whole before/after bytes of every touched document — is returned only on `plan { diffs: true }` (surface 4.5; the `summary` lines say what happens in words, and a client that executes by `plan_id` never needs the bodies); `plan_id` is the same either way since the preview is outside the digest. A malformed effect is `filter_invalid` naming `effects[i]` and the member, and the four shapes agents guess first carry a corrected call in `data.fix` (spec/mutate 3.4 §8): `at: "after"` as a bare string (the fix anchors on the block from its parent — `into: <parent>, at: { after: <id> }`), a plural `expect` nested guard-first (inverted to `{ <block id>: { content_hash } }`), `expect.max` inside an effect (moved beside `select`), a block `field: "text"` (`markdown`). The planner rejects contradictory effects before anything is touched — `conflicting_effects { effects: [i, j], focus }` by focus kind: one write per scalar focus (identical values dedupe), positional inserts/moves in order, nothing after a `remove` or on a descendant of a re-parsed block. `execute { plan }` commits exactly that plan: `unsupported_plan_version` for a foreign `version`, `plan_mismatch` if the plan was edited, `stale_plan` with current truth if a precondition moved (checked inside the transaction), else a receipt `{ plan_id, commit, revisions, new_ids: { "$new.0": "b_…" }, committed }`; `execute { plan_id, effects }` re-plans and commits only when the digest matches (`plan_mismatch { expected, actual }` otherwise). `apply { effects }` is plan + execute in one lock scope and transaction (use `plan` to preview). Effect-driven commits carry the intent in `commits.ops`. Since surface 4.0 every write tool except `observe*` is sugar over effects, built from one set of shared effect builders that the MCP server, both CLIs and the fixture runners use: the 20 sugar tools and `docs_update` build their effects and run plan + execute in one transaction, return the **receipt** (plus `hits`/`pairs` for `links_*`, `dangling`/`retargeted` for `docs_move`), carry the intent record in `commits.ops`, and have NO `dry_run` — preview any of them with `plan { effects }`, which writes nothing and burns no ids. Retired arguments (`apply.ops`, `dry_run`, `blocks_update.attrs`) fail `filter_invalid` with a message naming the replacement, and unknown arguments are rejected rather than dropped.

**Selectors (surface 4.1 / spec/mutate 3.1 §11.8).** `plan`, `execute` and `apply` also take `select`: an OQX query over `docs`, `blocks` or `nodes` whose hits drive the effects. Each effect in `effects` is then a template applied to every hit in result order: a template without a target writes to the hit itself (a `docs` hit is a document target, a `blocks` hit a block, a `nodes` hit a node); a target or a value may be `{ "oqx": "<expr>" }`, evaluated in the hit's row scope — `{ "op": "insert", "into": { "kind": "document", "_path": { "oqx": "project" } }, "at": "end", "markdown": { "oqx": "\"- completed: \" + _title" } }` appends a line about each hit to the document its `project` frontmatter names (`_title` the computed title; a bare `title` would read the authored key). The plan records each hit's origin as a row ref `{ _id, _path }`. The plan records `selection { query, expect, templates, cardinality, identities }` in its digest, so `execute` never re-runs the query and a changed hit set is `plan_mismatch`. Cross-hit collisions obey the focus rules (inserts into a shared target sequence; two different scalar values are `conflicting_effects`). `expect.max` bounds the selection and is required on a one-shot `apply`; exceeding it or the 1000-row ceiling is `selection_too_large` with nothing planned; zero hits is an empty plan. A target expression yielding nothing is `target_missing`, several `ambiguous_target`. `limit`/`order by` are allowed in the selector; `offset`, `distinct`, `values`, `links`, `follow`, nested `from` and counting consumers are refused as `filter_invalid`. `docs_set_meta` and `docs_create` write through the known-id path, so their blocks' dispositions read the api rule (`edited`/`inserted`, `api`) rather than the matcher's labels (bytes and ids unchanged).

`apply` with `ops` is the legacy block-op writer: a changeset of kernel ops (insert/update/move/remove/split/merge) applied atomically; each op is a tagged object keyed by `"op"`, targeting its `block`/`blocks` field (never `_id`/`target`). MCP-originated writes are actor `agent:mcp`; a successful non-dry-run write schedules a background embed drain.

Macros expand to `apply` ops through the same changeset machinery. Registered macros are exactly `blocks_check`, `nodes_set`, `blocks_append`, `docs_append`, `links_retarget`, `links_repair` — the once-specced `sections_rename`/`sections_move`/`lists_insert_item` are NOT registered MCP tools. `nodes_set` surgically edits one editable prop of a projected node (a link's `name`/`value`, a task's `checked`); it errors `node_not_editable` when the kind/prop has no editor. `blocks_append` (3.0, the former `sections_append` by heading id, generalized) appends INTO a block by what it is: a heading → the end of its section; a container (list, item, task, blockquote, table) → the end of its children; a leaf → `block_not_container` (`data: { id, type }`, the message pointing at `blocks_insert … at.after`). `docs_append` is additive and identity-preserving (existing blocks keep their ids); the doc must already exist (else `doc_missing`); with `section` (a heading's TEXT, `"Setup"` or `"## Setup"`) it appends at the end of that section — no heading in the document → `parent_missing`, the text spelled twice → `ambiguous_heading` with `candidates[{ _id, _doc_id }]` (pass the heading's id to `blocks_append`). `links_stale` is READ-ONLY (not a writer): it surfaces DANGLING internal links (`phantom:` edges) with `stale[]` + `externalCount` + `totalOpenEdges` + `truncated`, scoped by `path_glob`. Each row is the link under the `links` target's names — `{ _doc_id, _path, _block_id, _predicate, _provenance, _dst_kind, target, authored, _anchor, reason }` (`target`, `authored`, `reason` are roles; bare through 4.11, `srcDoc`/`srcPath`/`srcBlock`/`dstKind` before 3.0) — and carries both `target` — the canonical missing path, `/`-rooted like every path the surface returns (`/guides/old.md`) — and `authored` — the destination text exactly as written in the source block (`/guides/old.md#Setup`; `null` for frontmatter edges, which have no block). `summary: true` returns counts only (`staleCount`, `byTarget[{target,count}]`, `bySource[{_path,count}]`, `externalCount`, `totalOpenEdges`) for a repo-wide audit in one small call. Feed either `target` or `authored` into `links_repair` (batch of `{from,to}` pairs; `links_retarget` is its single-pair form) to fix them.

`links_repair` / `links_retarget` rewrite **link destinations, not substrings**: `from` must be the whole destination of a Markdown link/image `[t](dest)`, a wikilink `[[dest]]` / `[[dest|alias]]`, or a bare-path inline field `key:: /dest`. A leading `/` is optional on either side, and a trailing `#heading`/`^ref` fragment on the link is preserved and re-appended to `to`. Never rewritten: prose mentions, inline code, `code_fence` blocks, longer paths that merely contain `from` (`/b.md` does not match `/everland/b.md` or `/b.md.bak`), and frontmatter values (use `docs_set_meta`). Each destination takes the first matching pair (no chaining). Ops coalesce to one `update` per **top-most** block — a list and its list items carry the same bytes, and updating the container re-mints its children, so the child hit is dropped rather than failing `block_missing` mid-changeset. Scope source docs with `path_glob` (same glob rules as `links_stale`). Response: `hits[{ _id, _path, oldRaw, newRaw }]` (the rewritten block and its document), `pairs[{from,to,hits}]` (per-pair destination counts; `0` = nothing matched), `applied`, and the kernel result (`results`, `revisions`, `committed`, plus `diffs` on a dry run). The dry run (`dry_run` omitted or `true`) **plans through the kernel** in dry-run mode, so it fails exactly where the apply would.

`blocks_update` (with the other `blocks_*` sugar) resolves a block ref, pins `expect.content_hash` server-side, and runs one kernel `update`. Its `markdown` may parse to **several** sibling blocks: the target keeps its id and takes the first, the rest are inserted right after it with fresh ids; a list item may likewise be replaced by a multi-item list. The response adds `_id` (the target) and `ids` (every resulting block, in order — a role list, like `new_ids`) to the kernel result.

`docs_update` is the whole-document path with SMART identity preservation: submit the complete proposed `content` and the engine reconciles it against the current stable block tree, preserving ids for recognizably-same structure, minting for new, tombstoning removals. Since surface 4.0 it is sugar for the effect `set { target: document, field: "content", value }` and returns the **receipt** (`{ plan_id, commit, revisions, new_ids, committed }`; a `content` equal to the current bytes is zero effects, `commit: null`, nothing written). To see the identity decisions first, call `plan { effects: [that set] }`: the plan's `preview.identity[<doc id>]` is the whole-document planner's metadata — `matcher_v`, `summary` (preserved/updated/moved/created/removed/split/merged/ambiguous), `ops[{ op_index, disposition, blocks, confidence, reason, detail? }]`, `diagnostics` — then `execute { plan }` commits exactly it (`stale_plan` if the document moved on). A plan whose replay cannot reproduce `content` byte-for-byte fails `plan_not_convergent` with the diagnostics. The `{ opset, plan, result }` shape and `dry_run` are gone (4.0).

`observe` (ADR-014) is the whole-file **sync-ingest** counterpart: it records `content` as the current authoritative bytes for `path` as an **observed-origin** commit — a write *around* the engine (mirroring an external edit) rather than `docs_update`'s api-origin write *through* it. Both reconcile against the block tree and preserve ids; only `origin` differs (and thus the change-feed semantics + matcher path). `observe` writes **no file** (it is the file→DB direction), so it works on a headless/sourceless server; it is idempotent (bytes matching the stored revision are an echo — `echo:true`, `rev:null`, no commit) and flags git conflict markers (`conflicted:true`). Mirror a deletion with `observe_delete` (below), not `docs_delete`. Returns `{ _id, _path, rev, commitId, converged, echo, conflicted, dispositions[] }` (the store's own `{ doc, commit, rev }` outcome of `spec/store` is re-shaped at the surface boundary). `observe_many` is the batch form — an array of `{path, content}` under one timestamp + a single resurrection-pool sweep, returning one result per file. `observe`/`observe_many` are the single reconcile primitive (`observeOne`) that the local filesystem checkpoint and the external-source driver also share, so on-the-wire and in-process reconciliation cannot drift.

`observe_delete` (ADR-014) is the deletion counterpart: it records that `path` left the source scope by tombstoning the live doc as an **observed** deletion — its blocks are pooled for resurrection if the path reappears, and no file is removed (it is already gone from the source). Returns `{ _id, _path, deleted }`; idempotent, so a path with no live doc is a no-op (`_id: null, deleted: false`). Contrast `docs_delete`: an api-origin, intentional, non-pooled removal that also unlinks the working-tree file. A synchronizer mirroring an external delete uses `observe_delete`, never `docs_delete`.

> **As-built:** these doc-level tools are registered in the MCP server and back the CLI's `new`/`mv`/`rm --doc`/`meta`/`update`. `docs_set_meta` takes `set` (keys to set) and `unset` (keys to remove) rather than a single `patch` object; the per-op `expect` CAS guard specced in 04 is implemented on kernel ops (via `expect.content_hash`), while the doc-level tools re-ingest the whole file. Every write tool call — the 21 of `spec/surface` §4, dry runs included — runs under the cross-process writer lock (`spec/sync` §7) for its whole duration, taken once at the tool boundary, so `omg mcp` is safe beside one-shot CLI writers and the Rust `omgbase mcp`. MCP-originated writes are actor `agent:mcp`.

### History

```
blocks_history { _id, limit? }                                 // a block's biography, newest first (history_node before 3.0)
docs_diff { _id?, _path?, from_rev, to_rev }                 // block-grain diff between two revisions of a document (diff before 3.0)
docs_diff_unified { _id?, _path?, from_rev?, to_rev? }       // unified diff (Myers, 3 lines of context) of the two revisions' file texts (what docs_read_at returns); defaults to the last commit
docs_history { path_glob?, _id?, _path?, include_deleted?, limit? }  // per-document revision lists
changes_since { cursor?, epoch?, origin?: "api"|"observed"|"import", limit? }  // the change feed (store 17.0: the core's `feed`) → { digests, cursor, epoch, oldest, head, truncated }; a digest { commit, seq, ts, origin, actor, batch_id, plan_id?, summary, revisions: [{ _id, _path, _hash, kind, from_path? }] }; a cursor is (epoch, seq) — another epoch, cursor > head or cursor behind oldest − 1 is `expired_cursor { epoch, oldest, head }` → rescan (spec/sync §6)
```
`blocks_history` returns the commits that **changed** a block — inserted, edited, moved, split/merge lineage, resurrected — with disposition kind/confidence/reason (no `cursor` param); a commit that rewrote the document but left the block byte-identical in place is not listed (store 14.2: `same` verdicts are not persisted — through 14.1 every commit to the document appeared), so the newest entry's `ts` is the block's `_updated_at` and "present and unchanged in commit X" is a `docs_diff` question. `docs_diff` is block-grain only — `[{ kind: "added"|"removed"|"changed", _id, before?, after? }]` — there is no `grain` param; both `from_rev` and `to_rev` are required and the document is `_id`/`_path` (resolved first, so an unknown doc is a loud `doc_missing` rather than an empty diff). `docs_diff_unified` is the line-grain sibling — the `omg diff` rendering: `{ _id, _path, from, to, diff }` where `diff` is a real unified diff of the two revisions' reconstructed file texts (for each revision exactly the bytes `docs_read_at` returns — frontmatter, trivia and top-level order included, so hunk line numbers are real file lines and frontmatter may appear as context; split on `\n`; the empty text is zero lines): Myers' shortest edit script with a deterministic tie rule (the same in both engines, `spec/surface` §3), hunks with 3 lines of context that merge when their contexts touch or overlap, `@@ -a,b +c,d @@` headers (1-based start and length; a length of 1 written as the start alone; `a,0` for an insertion after line `a`), lines prefixed `-`, `+` or a space with nothing after the sign, no `---`/`+++` file header, `""` for identical texts. Its revisions are optional: `to_rev` defaults to the document's current revision and `from_rev` to the one before it, so a bare `{ path }` answers "what did the last commit change here" (a single-revision document diffs against itself; a document with no revisions is `target_missing`). `docs_history` groups revisions BY DOCUMENT — `{ _id, _path, deleted, currentRev, versions }`, each version a `revisions` row under the row's names, `{ _rev, _seq, _commit, _ts, _origin, _actor, _hash, _is_current, _archived }` (oldest→newest; `{ rev, seq, commit, updated_at, origin, actor, hash, isCurrent, archived }` through 4.11, `ts`/`contentHash` before 3.0; `_archived` since surface 4.9 — the revision's bodies live in an archive segment); require one of `path_glob`, `_id` or `_path`, `include_deleted:true` to also see tombstoned docs, `limit` caps documents with `truncated`. `changes_since` is the repo-wide COMMIT feed: `cursor` is the repo commit seq (NOT a `since_ts`; no `scope`/`min_confidence`), poll with your last cursor to cheaply re-orient after time away. The result is `{ digests, cursor, truncated, head }`: `cursor` is the last digest's `seq` (pass it back while `truncated`), and `head` is the repo's current max seq, so a caller can tell "nothing new" (empty page, `cursor == head`) from "this cursor is not from this repo/server" (`cursor > head`) — seqs are a dense per-repo order and a cursor is only meaningful against the `repo` it came from. Each digest's `revisions[]` carries `{ _id, _path, _hash }` (`_hash` = hex of the revision's rendered file hash; the same shape as an `apply` revision — `{ id, path, hash }` through 4.11, `{ doc, path, contentHash }` before 3.0; the digest's own `commit`/`seq`/`ts`/`origin`/`actor` stay bare — a digest describes a commit, not a row kind), so a synchronizer can decide "changed vs echo" against what it last wrote without a follow-up `docs_read`; `origin` filters to commits a given writer produced. Feed a `rev` from any of these into `docs_read_at` (whole doc at that rev) or `docs_diff` (changes between two revs).

### Admin

```
repos {}                      // list the workspace's repos: { repos: [{ slug, hasSource }] }
repos_status { repo? }        // { _id, slug, rootPath, docs, blocks, feed: { epoch, oldest, head }, openEdges, disk } — `_id` the root row's id (5.0); the feed's position replaces the v16 `commits` count and `unconverged` (store 17.0)
sync_status { repo? }         // { epoch, oldest, head, lastBatch: { ts, batchId, files } | null, convergent, diskChecked, disk, capabilities } (store 17.0; lastCommitSeq/lastCheckpoint through v16)
version {}                    // which engine + versions: { engine, version, components, specs, schema, mcp, runtime, commit, built }
```
`repos` enumerates the workspace's repos so a client can pick a `repo` slug for any tool (ADR-014). `repos_status`/`sync_status` report on the addressed repo (or the bound default). `repos_status.disk` is a read-only working-tree scan (`changed`/`deleted`/`untracked`/`checked`). `sync_status.convergent` is true ONLY when the DB is converged AND a working-tree scan ran and found no drift — never green while disk freshness is unverified. There are no `repos_create`/`sync_flush` tools on this surface (repo lifecycle lives in the CLI/store, not the MCP server). `version` (spec/surface §4, 1.4) is how a client learns which engine it is talking to and what it was built from: `engine` (`typescript` here, `rust` for the port), `version` (the serving binary's own — the `omgbase` npm package), `components` (every omgbase package the binary is built from: `omgbase`, `@omgbase/core`, `@omgbase/oqx`, `@omgbase/sync`, `@omgbase/fs-adapter`, keys sorted bytewise), `specs` (the `spec/<x>/VERSION` each was built against — compile-time constants, `SPEC_VERSIONS` in core), `schema` (the database's `PRAGMA user_version`), `mcp: { protocol, sdk }`, `runtime` (`node <version>`), `commit`/`built` (from `dist/build-info.json`, written by `pnpm build`; `null` when unknown). No arguments, no repo scope. `omg version` renders it; `omg version --server …` renders the remote engine's answer.

## 4. Tool-description contracts (write these into the MCP descriptions)

- IDs are stable within and across sessions; locators are display-only. Prefer IDs in follow-up calls (prompt-cache-friendly).
- After any conflict, the error already contains current state — retry from it, don't re-read.
- `links_retarget`/`links_repair` and any multi-doc write: preview with `plan { effects: [{ op: "retarget", … }] }` first — the plan's `preview.retarget` lists the hits and pairs and the plan burns nothing (4.0; before, `dry_run: true` ran the kernel planner, so it failed where the apply would).
- Never rewrite whole documents to make small changes; use block ops. A blind `docs_put`-style blob overwrite intentionally does not exist — whole-document submissions go through `docs_update` (`dry_run: true` to plan first), which reconciles against the block tree to preserve identity rather than replacing it. Reserve those for genuine whole-doc rewrites.
- `changes_since` with your last cursor is the cheap way to re-orient after time away.
